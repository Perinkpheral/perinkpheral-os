# perINKpheral

A desk e-paper display built on ESP32-C6, with four buttons. Its software is a specialized operating system for e-paper, built on FreeRTOS/ESP-IDF. Perinkpheral OS runs WebAssembly applications installed from a catalog without reflashing the firmware.

Use `perinkpheral` in code and domain names, `perINKpheral` in prose headings, and `perINKpheraL` in the wordmark. This repository is `Perinkpheral/perinkpheral-os` (renamed from `perinkpheral` on 2026-11-20, before the public release; its Pages address moved with it, so a firmware older than 0.1.69 finds a new release and cannot fetch it - it is updated once through recovery). The pun: peripheral vision + peripheral device + ink. The operating system is named **Perinkpheral OS** in both English and Russian. Use that name in prose instead of "host" when referring to the operating system. Network hosts, computer-side tests and existing API identifiers keep their technical names.

This file defines the vision, architecture, conventions, milestones and current state. Next to it are only references: `AGENTS.md` - the bench, build and flash recipes, what must not be touched in the driver; `hardware/README.md` - everything found out about the panel, with the datasheet and links; `SECURITY.md` - who could take what from the device, what stands in the way and what does not; `CHANGES.md` - what each release brings, its notes on GitHub, in the flasher and on the device's page. `docs/testing/stability.md` - the plan of stability testing: a soak on the device, fuzzing, a monkey in the simulator, a loss of power. `docs/decisions/` records decisions and studies; check there before reopening a question. Where they disagree, this file wins.

**Everything in this project is written strictly in English**: code, comments, commits, documentation, this file, the device's web page. What is translated is translated beside an English original, which is the one that is right when the two differ: the application guide's Russian (`docs/guide/source/guide.ru.txt`, built into `perinkpheral-app-guide.ru.pdf`; the owner, 2026-11-14), the user manual's Russian (`docs/manual/source/manual.ru.txt`, built into `perinkpheral-manual.ru.pdf`; the owner, 2026-11-21), and what the device says - Perinkpheral OS's own words (`firmware/components/words/words.c`) and the strings of an application (`strings/<language>.json`), in English and Russian today. Names are never translated (E-Ink, SDK, Watchdog, the calls and constants). The firmware's fonts carry ASCII; letters beyond it come in glyph packs, and what has no glyph is spelled in ASCII (see "Text is bytes").

## Vision and philosophy

**Vision.** A separate screen for the desk that is not a second monitor: it can be ignored until it is needed and read out of the corner of the eye - a line of the schedule, the current track. In one phrase: a TRMNL without the server and with buttons. The goal is an extensible operating system with its own applets on hardware anyone can repeat, and a community of builders and application developers.

**Principles**, in the order they win arguments:
1. **Peripheral, not a monitor.** No backlight, nothing that moves, nothing that asks for attention. The device is silent until it is looked at, and what it shows is readable at a glance. This is why it is e-ink and why the refresh policy is conservative.
2. **Not a thin client.** The device does the work itself: it fetches the data, runs the application and draws the frame. No server prepares pictures for it, the vendor's or the user's own.
3. **The user's data stays the user's.** Showing a calendar must not require binding an account to a machine the user does not own. Requests go from the device straight to the source; there is no cloud of ours in between and there never will be.
4. **It has buttons.** A companion is something you can answer, not a picture frame: applications react to presses, and the user is always one long press away from taking the screen back.
5. **Battery operation.** It can run on its battery and charges over USB-C; battery life is not specified in version 1.
6. **Cheap to repeat.** Common DIY parts, no custom PCB, and a case intended for FDM printing in PLA, PETG or ABS, with optional TPU feet. If a choice makes the device harder to build at home, it needs a very good reason.
7. **The user decides what is on the screen.** Not a fixed set of dashboards: an SDK and applets that anyone can write and install without reflashing. Perinkpheral OS provides shared services; applications define the content and interactions.

What follows from this: no backend of our own, no accounts, no telemetry; a static catalog instead of a store service; TRMNL compatibility as one application, not as the platform; project code under MIT, with separate licenses retained for fonts and dependencies.

The hardware, assembly and case renders are documented at https://perinkpheral.dev/hardware (source: `perinkpheral-dev-portal/src/pages/Hardware.tsx`); the case model is `hardware/step/rev1/perinkpheral.step`; the renders are in `hardware/render/` (not in git).

### Wiring
```
Display → XIAO
  VCC  → 3V3
  GND  → GND
  DIN  → D10 (GPIO18, MOSI)
  CLK  → D8  (GPIO19, SCK)
  CS   → D7  (GPIO17)
  DC   → D5  (GPIO23)
  RST  → D4  (GPIO22)
  BUSY → D6  (GPIO16)

Button module → XIAO
  V → 3V3
  G → GND
  1 → D0 (GPIO0)
  2 → D1 (GPIO1)
  3 → D2 (GPIO2)
  4 → D3 (GPIO21)

Battery → XIAO
  BAT+ → BAT+ pad (bottom, next to "D5")
  BAT- → BAT- pad (bottom, next to "D8")

Free: D9 (GPIO20, MISO - the display does not need it).
```
The wiring is fixed and done - do not change it. Battery voltage and USB supply voltage are **not measured** in version 1 - decided, do not propose dividers or ADC for it. Version 1 promises no battery life: autonomy is conditional and undocumented (the owner, 2026-11-24). A battery ADC and its driver may come in version 2. The power profile is a Perinkpheral OS setting. Auto uses the existing USB Serial/JTAG connection to a USB host; this does not detect a charger or tell which source powers the board.

### Board specifics worth knowing
- Not on the header and not to be touched: GPIO9 (BOOT, strapping), GPIO15 (user LED), GPIO12/13 (USB D-/D+), GPIO3 and GPIO14 (the antenna switch - driven only by `firmware/components/board`).
- Antenna: at start GPIO3 → LOW (enables the RF switch), GPIO14 → LOW (ceramic) or HIGH (external U.FL). Without this Wi-Fi may work poorly. Done by `firmware/components/board`, the choice is `APP_ANTENNA_EXTERNAL` in menuconfig.
- GPIO16/GPIO17 are the chip's UART0 TX/RX, here they are the display's BUSY and CS. The console is on USB-JTAG only. The ROM bootloader still prints its boot log into GPIO16 at every reset (tens of ms) - no panel failure was observed on this bench.
- GPIO0-2 are the LP group: the buttons are on them, the display stays off them.
- **The way out when the main firmware has stopped answering: buttons 1 and 4 (UP and BACK) held together for ten seconds restart it.** The press is an interrupt and the ten seconds are counted by a timer whose callback runs in an interrupt (`firmware/components/input/buttons.c`), so it does not wait for the main event loop, the buttons' task or the scheduler; interrupts turned off for good are ended by the interrupt watchdog, as always. Nothing on the screen offers it - it is for when the screen cannot; Settings has Restart for when it can. Recovery reads OK and BACK directly and does not run this interrupt-based rescue combination. Written and built; tried on the device by hand and working (the owner, 2026-11-24).
- From light sleep any of the four buttons wakes the device (`gpio_wakeup_enable`). Deep sleep - not used in version 1 - is another matter: its wake-up on the C6 is ext1 on GPIO0-7 only, so buttons 1-3 would wake the device and **button 4 (GPIO21) would not**.
- Flashing over the native USB Serial/JTAG (`/dev/ttyACM*` on Linux, `/dev/cu.usbmodem*` on macOS), `idf.py flash`. Entering the bootloader: hold BOOT while powering up or resetting.
- 3V3 gives up to ~700 mA for everything. On battery the 5V pin is empty.
- Over-discharge protection is entirely the battery's PCM. Charge level and power source are not shown on the screen - there is no data.
- Charge LED: blinks while charging, off when full. The CHRG signal is not routed to a GPIO.

## Stack
- ESP-IDF 5.5, C. No Arduino, ESPHome, LVGL, GxEPD2.
- Application runtime: **wasm3** v0.9.0 (interpreter, sandbox). Applications are built with wasi-sdk (found through `WASI_SDK_PATH`; verified with 34); the firmware build needs it too, since the firmware carries its system applications.
- **Firmware and SDK tools share one Kotlin implementation** (the owner, 2026-11-15: "not two toolchains"). `tools/core` owns the contract reader, package formats, build flags, catalogs, device client and simulator network; `tools/cli` exposes them through `tools/perinkpheral` and holds the generators. The CLion plugin uses the same core. Java 21 or later; the launcher builds the jar with Gradle when its sources change. `flags` supplies the same compiler flags to CMake and the plugin; `headers` permits incomplete translations while editing, which `build` refuses. **Firmware and SDK generators and checks stay in Kotlin** (the owner, 2026-11-17). ESP-IDF's Python and the separate Home Assistant integration are outside that toolchain. The enclosure exporter in `tools/case`, added on 2026-11-18, is a separate Python 3.12 CAD utility for STEP/3MF geometry; it is not a replacement for `tools/core` or `tools/cli`. External tools: a C compiler for preview and simulation, ffmpeg for video, Chromium and poppler for PDFs.
- Fonts: the square one (code, `font_square.c`) for the logo; for everything else one of two families, the user's choice (`font` in the settings; Font in Settings on the device, and on the page). **Departure Mono**, a monospaced pixel font and what a device starts with: one bitmap of it at its own 11 px from `tools/perinkpheral font`, drawn at whole multiples - 22 px for Perinkpheral OS, and 11, 22, 33, 44, 66 and 110 px for applications. **Jersey** is heavier and proportional. Its four faces - Jersey 10, 15, 20 and 25 - are rasterized on their own pixel grids and provide approximately corresponding size classes. Their cap heights, line heights and character widths differ from Departure Mono's; applications must measure the selected font for layout. Applications ask for a size by its id and get it in the family chosen. The fonts are ASCII; the letters beyond it come in glyph packs.
- FS: LittleFS (partition `apps`, 640 KB). NVS twice: Perinkpheral OS's settings in the partition `nvs`, the applications' `kv_*` in one of their own, `appkv` (56 KB), so that nothing an application keeps can crowd the settings.
- Network: `esp_http_client` (TLS through mbedTLS), `esp_http_server` for the web UI.
- Main firmware carries a hash-verified, build-local mbedTLS patch accepting NumericString X.509 name attributes; recovery is untouched, and an upstream source mismatch stops configuration (decision [0008](docs/decisions/0008-moex-tls.md)).
- The display driver is our own: init, full refresh (and Waveshare's fast one), partial refresh of a window, panel deep sleep. The bytes are clocked out by hand over GPIO, as a SPI master in mode 0 would, with **CS toggled per byte** - otherwise the refresh never finishes (see `AGENTS.md`). The SPI driver of ESP-IDF sent the same and spent 17 of every 21 microseconds getting ready for a byte; by hand a byte is 8.
- Buttons: `gpio_config` input without the internal pull-up (the pull-up is on the module), active LOW, debounce 20 ms. A press is reported as it happens (down, up) and as what it meant (short, or long at ≥600 ms).

## Memory budget (the hard limit of the C6)
- SRAM 512 KB, shared by Perinkpheral OS, the application area, Wi-Fi and TLS. There is no PSRAM and there will be none.
- Flash 4 MB: `appkv` 56 KB, a factory recovery image of `0xE0000` (896 KiB) and one `ota_0` slot of `0x200000` (2 MiB), `appcode` 320 KB, LittleFS `apps` 640 KB and `glyphs` 64 KB (`firmware/partitions.csv`). Main must fit `ota_0`; recovery must fit `factory`. Builds check both independently. The map service's land and code take 233 KB of main (the release image went from 1,366,304 to 1,599,760 bytes on 2026-11-23, 497,392 bytes of the slot free); recovery does not carry it. Both firmware builds use `-Os`; the release has no development tools (`sdkconfig.release`). The web page is gzip-compressed. CI reports image and RAM sizes against the preceding successful build of `main`. The partition table cannot change over the air.
- A wasm application's memory is **what its stack and data take, at most 64 KB**, and cannot grow (`docs/decisions/0011-page-32k.md`). Build: `-Wl,--page-size=1 -Wl,--no-growable-memory -Wl,-z,stack-size=8192` (`tools/perinkpheral build` does it): the module declares one-byte wasm pages, which the interpreter reads, so its memory is sized to the byte. The builder refuses a module whose memory may grow or is over 64 KB. The interpreter is built with a limit of one standard page: a larger module does not load, and a module made by other means that declares a growable memory grows no further than 64 KB, inside the application area. A module linked for one standard page (64 KB) loads as before. The build reports the memory and the estimate of the running code together against the application area.
- **One** wasm instance is loaded at a time. Background delivery unloads the scene, loads the owner and delivers the answer, then restores the scene unless the owner takes the screen. Its session survives this swap.
- **Sockets are counted** (`web_server.c`): lwIP has 12; the web server keeps three of its own, the setup access point's name server one, the poller one for the request it makes; the page's connections are the seven left, the oldest closed for the next. Promised more than are left, a connection finds no socket while the server still has room, nothing is closed and the page is dead (seen 2026-11-17, "error in accept (23)").
- **Heap admission** (`firmware/main/memory.c`). Wasm memory and interpreter allocations use the application area. Perinkpheral OS services allocate separately: a network session requires 60 KB free and a 17 KB contiguous block; a web route declaring `MEMORY_FOR_A_PAGE` requires 24 KB free and an 8 KB contiguous block before its handler runs; `/api/screen` declares `MEMORY_FOR_A_PICTURE`, 40 KB free and a 16 KB block, for its 15 KB copy of the frame. `POST /api/glyphs` declares `MEMORY_FOR_A_GLYPH_PACK`: admission uses the declared body size (at most 32 KB) plus two 4 KB compaction buffers, with 24 KB total and 8 KB contiguous spare. It therefore requires the body size plus 32 KB free and the body size plus 16 KB in one block (64 KB / 48 KB for a maximum pack). This covers allocator overhead and leaves the page's usual spare heap after upload and compaction allocations. Admission observes memory rather than reserving it; an upload allocation that still fails returns the same 503. Routes declaring `WEB_NO_MEMORY_NEED`, including the page, status and settings routes, bypass that admission check. Recovery handles firmware uploads without this admission check. A refused web request returns `503` with "Not enough memory." A waiting route that needs a session (`/api/catalog`, `/api/apps/install`) is asked on arrival only for a page's worth, for what its handler takes itself: its download is the poller's, follows the poll in progress, and the poller asks for the session's room then (`run_fetch_job`); asked for it on arrival, the poll's own session refused it ("Device busy", 2026-11-26). Such a request waits as long as the poll in front of it - up to a minute for a picked answer, five for a streamed one - and holds the one waiting slot meanwhile. Applications receive `HOST_FAILED_NO_MEMORY` after waiting up to six seconds. The poller's looks while it waits are not refusals (`memory_peek`); the refusal is counted once, when it gives up. Catalog reads, app installs and glyph uploads retry explicit memory/busy refusals and interrupted downloads up to three times, after 2, 4 and 8 seconds. Exhausted busy or memory retries say "Device busy. Try again shortly." Exhausted download retries keep "Download failed." Lost responses and permanent refusals are not replayed: a lost response may follow a committed installation. Critical pressure means less than 12 KB free, a contiguous block below 4 KB, or a new allocation failure. The first check closes web connections; three consecutive checks, five seconds apart, trigger an orderly restart. A ten-minute period of session memory refusals also triggers a restart. Observing enough total and contiguous memory - by the five-second look, a counted question or the poller's uncounted one - clears that period even if the next poll is not yet due. `/api/status` counts refusals and failed allocations.
- The application area is 112 KB, one heap: the module's memory is taken from it and the rest is the interpreter's, so an application with little data has more room for code (weather: 9.7 KB of memory, about 102 KB left). At 144 KB the heap left to Perinkpheral OS stayed under the 60 KB a session needs and requests were refused. Perinkpheral OS keeps the rest of the heap. Wi-Fi buffers are bounded in `sdkconfig.defaults`; IPv6 is disabled. Received frames are copied out of the Wi-Fi driver at once (`CONFIG_LWIP_L2_TO_L3_COPY`, main and recovery), so unread socket data does not hold the driver's receive buffers: without it, recovery waiting for OK with an upload unread lost the access point (2026-11-22). Current free heap, its low-water mark and its largest block are reported by `/api/status`; bench measurements from older builds are not a memory budget.
- An HTTP response body that is not picked goes to the application as a stream, in pieces of up to 1 KB, while TLS is open; Perinkpheral OS never holds it whole. The 112 KB application area above is reserved at startup, independently of how much an instance uses; TLS and Perinkpheral OS need room outside it. If reservation fails, boot logs an error, `/api/status` reports `app_area_available: false`, and applications fail explicitly with "App memory unavailable." on the existing cannot-start screen. Main keeps running so the page and recovery entry remain usable; freeing heap later does not repair a missing boot reservation.
- Two 400×300 monochrome frames require 15,000 bytes each: the composition buffer and the display service's retained frame.

## Architecture

FreeRTOS/ESP-IDF provides the native task scheduler and low-level system services.
Perinkpheral OS manages applications and their shared API, screen, storage and network
access. One WebAssembly instance runs at a time; background responses load their
owning application and then restore the scene.

### Application
**Feature freeze until the public release** (the owner, 2026-11-20): bugs, UI/UX and the polish of applications only; no new call, application or mechanism. The order to the release: manual acceptance (`docs/testing/acceptance.md`), fixes, the endurance run (`docs/testing/stability.md`), fixes, load testing (`docs/testing/load.md`), the release - at which ABI 3 is frozen in fact. The owner admitted manifest poll methods and bodies under the freeze on 2026-11-21: "polls are GET only - extend the host API; an important change, taken in under the freeze". The map service (`gfx_draw_map`, `gfx_map_point`, `gfx_draw_map_radius`, 0.1.94) was ordered by the owner on 2026-11-23 as an addition under the freeze, for ISS and Earthquakes. ABI 3 stays 3.

**ABI 3 is the application contract; its first firmware is 0.1.30.** The supported set is explicitly `{3}`; ABI 2 is refused with "Update the app.", with no adapters. The manifest's ABI is retained through parsing into `app_load()`, which selects the supported contract before running code. Firmware releases and ABI generations are independent. An existing name, signature, privilege, binary layout, constant, accepted input or observable meaning cannot change within ABI 3, except that `HOST_ICON_COUNT` may increase when contiguous icon IDs are appended. A changed signature or meaning requires a new ABI while Perinkpheral OS retains the frozen generations it supports; additions after the 0.1.30 ABI floor carry permanent `HOST_SINCE_<name>` introduction stamps. New flags, exports or manifest behaviour that cannot be inferred from imports require an explicit firmware minimum. A new fixed struct layout needs a new call/type; `answer_info` alone permits extension after its unchanged prefix.

`tools/perinkpheral contract snapshot` records `sdk/abi/3.txt`; `contract check`, run by the host tests and CI, refuses removal or alteration of recorded entries, except that `HOST_ICON_COUNT` may increase when contiguous icon IDs are appended; it also refuses unrecorded additions; an addition is recorded with `contract snapshot`. Until the first public release the owner may still break ABI 3 (2026-11-20: "we are moving to production, not there yet"): `contract snapshot --unfrozen` rewrites recorded entries, and is not used after it. It checks actual wasm32 sizes, alignment, field types and offsets with wasi-sdk, plus names, wasm function types, privileges, constants and introduction stamps. Snapshot writes enforce the same rule for existing entries unless `--unfrozen` is authorized. Package hashes are recorded separately in `sdk/abi/3/fixtures.txt` and checked by the same command. The frozen Probe, Hello and Settings packages under `sdk/abi/3/`, their manifests and translations and Hello's four-byte little-endian saved count are test inputs, never rebuilt by tests. The build checks the actual import and export types against the contract. The device page uses one ABI-and-firmware predicate for Install, Update and Update all; `/api/status.supported_abis` is the exact supported set. Downloaded manifests remain authoritative.

`/apps/<name>/manifest.json` and the application's files on the LittleFS partition; its module, `app.wasm`, arrives there and is moved into the code partition (see Memory). **`firmware` is the minimum compatible firmware version** (the owner, 2026-11-16): the build (`tools/perinkpheral build`) computes the minimum from imported calls, exported contract handlers and detected manifest features - `HOST_SINCE_<call>` in `sdk/host_api.h`, a permanent line for every added call after the first firmware, `HOST_FIRMWARE_FIRST` for the rest - and takes the maximum of those stamps, the ABI floor (`HOST_ABI_3_FIRMWARE_FIRST`, 0.1.30, the first firmware of abi 3), the `HOST_SINCE_POLL_METHOD` stamp for a poll with a non-GET `method` or any `body`, and an explicit manifest minimum for other behaviour rather than a call; the catalog's index carries it. Poll methods and bodies require no hand-written minimum: the build computes it from the contract stamp, introduced in firmware 0.1.80. A rebuilt catalog asks no more of a firmware than its applications' calls do (the owner, 2026-11-17: stamping the SDK's own version raised every application with every release - a bug). `VERSION` at the root of the repository is the least version of the next release: CI releases the greater of it and the highest matching version tag with its patch incremented, so it is raised by hand only for a new minor or major version, or for a call whose `HOST_SINCE_` needs a version no release has yet - none may be past it. Perinkpheral OS does not start an application made for a newer firmware ("Update Perinkpheral OS.") and does not install one; the page offers neither its installing nor its update, and says which firmware it needs. Perinkpheral OS reads `name`, `title`, `version`, `author`, `abi`, `firmware`, `fullscreen`, `system`, `writes_files`, `icon`, `polls` (with `url`, `every`, `headers`, `method`, `body`, `pick`, `each` and `prefix`), `hosts`, `settings`, `intents`, `companion` and `certificates`, checks each, and skips a key it does not know. A poll is an `http(s)` `url`, an `every` of 10 seconds to a day - a number, or `"{{key}}"` of a setting whose value is the pace as a person writes it ("15 min", "1 h"): the user's choice, taken by Perinkpheral OS with no code in the application - and up to four `headers`; there are at most four polls, and the application knows each by its number. `method` is GET by default, or POST, PUT, DELETE, PATCH, HEAD, PROPFIND or REPORT, as `http_send` accepts. An optional text `body` fits in 1024 bytes before and after expansion; its presence with GET or HEAD is refused, even if empty. Content-Type comes from `headers`. `{{key}}` in a URL, header value or body is replaced from the application store (`text_template.c`). Body values are substituted as stored, including line feeds and UTF-8, without encoding or list joining; a carriage return in a value fails the request with `HOST_FAILED_NOT_READY`. The developer supplies the body's escaping, including JSON or form escaping. `name` is 1-13 of `a-z`, `0-9`, `-`, `_`: it is the folder, the key in the catalog and, as `a.<name>`, the NVS namespace of the application's store, and it must be the folder's name. `title` is at most 23 characters. `author` is optional for loading legacy packages and required for catalog publication: 1-63 UTF-8 bytes, without control characters or leading or trailing spaces. `Perinkpheral` is reserved for publication through the official repository. `description` - what the application does, in a line of up to 95 characters, translated as the title is - is the page's and the catalog's: the runtime manifest parser does not retain it; the firmware web handler returns it, using the manifest translation when available. The page shows it under the title in the Catalog (the index carries it, and every language's title and description of the package as `translations`) and in what an application is. **Texts a person reads are counted in characters** - a title, a setting's title, help and options - and have a byte limit of twice that value; the fields of the contract that hold such text have a room in bytes - a notice's line and the header's text 63, a cell's name and value 47 - whose character capacity depends on the UTF-8 encoding, and Perinkpheral OS cuts a text that is too long between characters, never inside one. The module is at most 48 KB (`MANIFEST_MODULE_MAX_BYTES`; the build (`tools/perinkpheral build`) refuses a larger one), in whole sectors of the code partition; what it has to fit when it runs is the application area (see Memory). A first flash comes with the catalog applications `firmware/preinstalled.properties` names, in the partition image (`APP_BUNDLE_APPS`; see Catalogs). **An application may bring an icon**, in its manifest and optional: `"icon"` is 11 rows of 11 characters, `#` for ink and `.` for paper - the form Perinkpheral OS's own icons have in the source, which a person can type, which follows the icon rules by construction and which scales. The device draws it beside the title in its menu, a cell two pixels; the web page draws it on the application's tile; a catalog's index carries it, so its icon is visible before installation.

**Settings are declared in the manifest, not by code**, the way Pebble did it with a companion page: nobody types a token with four buttons. Installed apps lists the installed applications; a gear opens a settings form drawn from the manifest without running the application. Catalog is a separate section. A field is a `text`, a `secret` (the page can write it and cannot read it back), a `number`, a `choice` from a list of `options`, a `toggle`, a `place`, a `url`, a `link` or a `list` (items of up to 63 characters, as many as the value holds, stored with a line break between them, added and removed by the row on the page; its `default` is a list); it has a `key`, a `title` and may have a `help` line, a `default` and `"hidden": true` - for a setting something else writes, an integration through `/api/apps/settings`, which the page's form leaves off (HA Companion's server and token, written by the Home Assistant integration) - what an absent setting reads as (the owner, 2026-11-15): `kv_get` returns it, `{{key}}` is it, the page shows it, and nothing is stored until the user saves. At most 8 of them, a value at most 255 bytes. Settings saved through the web API contain printable ASCII only; lists may also contain line feeds between nonempty items. Application KV values may contain arbitrary bytes. A `url` is the address of the user's own server - `http://192.168.1.10:8123`, a scheme and a host and maybe a port, nothing after - and the one setting a poll's URL may begin with and `hosts` may name: `"url": "{{server}}/api/states"`, `"hosts": ["{{server}}"]`. That is how an application for Plex or Home Assistant is written once for everybody's server. A `{{server}}` entry authorizes that configured host; other destinations must be declared separately. Changing a url/link destination whose previous stored or default value is nonempty first deletes all declared secrets, including supplied replacements. It then writes destinations before the other supplied values, including replacement secrets. Writes are not transactional: a failed save can leave a supplied secret deleted. The `url` setting is the user's to write and the application's only to read: `kv_set` on it is refused, or an application could move its own server - and the token with it - wherever it liked. A value that goes into a header or stands as the server is looked at again when it is used, whoever stored it: one with a carriage return in it fails the request, and a list's line breaks become commas: `{{key}}` of a list is its items, joined with commas, each encoded in a URL and as it is in a header. A `link` is a whole address the user was given - a calendar's secret `https://host/path?key` - and is the whole of a poll's URL (`"url": "{{feed}}"`, `"hosts": ["{{feed}}"]`): a `{{feed}}` entry authorizes the configured host; other destinations must be declared separately. Like `url`, the setting is writable by the user and read-only to the application; the page takes `webcal://` for `https://`. A public manifest default may be shown as text; a custom stored link is returned only as set or not set. An empty non-secret setting saved through the web API overrides the default; an empty secret deletes its key. `kv_set(..., 0)` deletes a key and restores its default. A `place` is asked for by its name: the page offers places as the name is typed (the browser asks Photon, a search of OpenStreetMap; the device does not) and fills the two `number` settings the place names as its `latitude` and `longitude`, which it does not show. The values are stored in the application's own store under the keys the manifest names, so the code reads a setting with `kv_get` by the same key, and Perinkpheral OS substitutes it into URLs and headers (`{{key}}`). A change arrives as `app_on_settings()`; an application that is not on the screen is loaded for the call and unloaded after it, as for data.

**The developer supplies translations; Perinkpheral OS loads the selected language.** An application's `strings` folder holds a file a language - `en.json`, `ru.json`, each an object of the same keys; the build (`tools/perinkpheral build`) makes `strings.h` of them (`STR_NO_EVENTS`, `app_string(id)`), builds English into the module and writes a table for every other language beside it (`strings.ru`, a file of the application's). When an instance is loaded Perinkpheral OS copies the table of the device's language (`language` in the settings; Language on the page) over the English one in the application's memory - when there is one, it is sound and it fits; else the application speaks English - so reading a string costs the application no code and no call. `text_fill` puts arguments into `{0}`, `{1}` of a pattern, in whatever order the language has them. The build fails on a language the system does not know (`sdk/languages.json`: the languages, and the glyph packs each needs), on a translation that lacks a key or has one too many, and on a letter the language's glyphs do not have. No plural forms. **What of the manifest a person reads** - the title, a setting's title and help, the labels of a choice's options - is translated in the same file under the key `manifest`, held by the build to the manifest itself and written beside it (`manifest.ru`); Perinkpheral OS takes the title from it for the menu, and gives the page the settings in the device's language, an option keeping its value and gaining a label. **Perinkpheral OS's own words** - what the buttons of its notices do and of the picker and the date-and-time screens (`ui_draw_picker`, `ui_draw_date` with no words of the application's: Save, Next, Back, Cancel), its questions, why an application has nothing to show, the names of days and months - are one table (`firmware/components/words/words.c`), English and Russian, in the firmware. Every application of the catalog has Russian. The system applications have Russian too: they have no files, so their tables are embedded in the firmware beside them (`launcher_system_file`). The device's page speaks the device's language too, in the same terms (`firmware/main/web/js/i18n.js`: a word of the page and its Russian, the device's answers among them; whole texts are put into the language where they stand, texts made of parts through `t()`); the page remembers the language in the browser and is read anew when the device says another. The cities a time zone is chosen by are one list, `firmware/system/settings/cities.json` - each city's English name, its Russian, its POSIX zone and the IANA names a browser may give it: `tools/perinkpheral cities` makes Settings' `cities.h` of it (the host tests hold the two together), the page carries it (`<!-- data: -->`; the device's limits - how many applications and sources, a setting's length - come from the firmware's headers the same way, `<!-- defines: -->`), and both show the cities in the device's language, sorted by the names shown; the city chosen is Perinkpheral OS's setting `tz_city`, so the device and the page show the same one of those that share a zone. Still English: what the crash record and the build say of themselves.

**A companion page** is for what a form cannot do - signing the user in somewhere, choosing from what is there. `"companion"` in the manifest is its address, `https` only: a static page of the application's author on any hosting. The device's page opens it in a window from the application's settings (Set up), and the two talk in messages: the companion says it is ready, gets the application's settings and what is set (no secrets), and hands back values for keys the manifest declares; they go into the form, and the user saves them. Nothing of it runs on the device and nothing passes through a server of the project's. `sdk/companion/example.html` is a sample. The form accepts companion results only for fields present in it; hidden settings have no field and are written through `/api/apps/settings`. Secret and link values are omitted from the message sent to the companion.

**Manifest polls of every method can use Perinkpheral OS JSON picker.** A poll declares paths such as `current.temperature_2m` or `daily.weather_code[0]` in `pick`; Perinkpheral OS extracts their values and delivers `app_on_picked`. Polls without `pick` and explicit HTTP requests deliver chunks through `app_on_data` for the application to parse. The picker is one source, `sdk/lib/json_pick.c`, built into Perinkpheral OS and into any application that wants it: an answer to a request of an application's own comes in pieces, and the application feeds them to a picker of its own. Ease of writing an application is worth Perinkpheral OS's memory here. A path may have `[*]` in place of one index - `close[*]` - for every element of an array, kept as text in a buffer of 8 KB Perinkpheral OS takes for the answer and gives back after it (`HOST_LIST_BYTES`); `app_value_series()` turns them into a series for `ui_draw_chart`. Numbers with decimals are `sdk/lib/app_fixed.h`: integers of 64 bits with so many decimals, read from text with an exponent, divided and written with rounding half away from zero.

**HTTPS** verifies servers against the root bundle carried by ESP-IDF. An application may bring up to two certificate-authority roots in its package, PEM or DER, at most 4 KB each (the owner, 2026-11-15). The build checks that each is a currently valid authority certificate. The poller adds them to the browser root set for that application only; the page asks about them before installation. A self-signed server certificate is not an authority root. The owner decided on 2026-11-12 that a user-supplied server certificate belongs in an application setting and must trust only that application's hosts. That setting is not implemented.

Response headers beyond `answer_info` are available through `answer_header` (firmware 0.1.51).
Perinkpheral OS retains up to 1024 bytes of names and values for the active response;
repeated fields are separate. If the complete set does not fit, every `answer_header`
call returns `HOST_ERR_NO_SPACE`; `answer_info` remains available. Undersized output
buffers also fail without truncating credentials. Redirects discard previous headers.
Applications implement authentication themselves and can keep a small session in their own
KV store when it changes. Scene/session RAM is not a background credential store.

### System applications and the system API
Perinkpheral OS's own pages are applications too - written with the same SDK, run by the same interpreter - so that Perinkpheral OS is built with what it gives to others. They are **system applications**: built from `firmware/system`, carried inside the firmware image (an update over the network brings them along, so they always speak the API of Perinkpheral OS they run on), never installed and never removed, and not counted among the installed ones. Their names begin with `sys.`, which no installed application's name can. `Settings`, `About` and the setup screen are bundled. `Settings` is the device's settings with four buttons and no keyboard: General (date and time - from the network or by hand, the time zone by a city from a list, power saving: Disabled, Always or Auto), Apps (the installed ones, each can be removed), Appearance (the font - Departure Mono or Jersey - the clock in the header, the default application and how long the menu waits before giving it the screen), Display (the three numbers of the refresh policy and Fast refresh), Wi-Fi (the network, the address, forgetting it - which turns Wi-Fi off - and, with Wi-Fi off, Connect to Wi-Fi), Restart and Reset - each of the last two a question. A value is changed on a page of its own with Save and Cancel (the picker); a long choice - the time zone's city, the default application - is a list with a check on what is set. Nothing is typed: a value is one of a few stepped through with UP and DOWN, a date is its parts stepped the same way with OK to the next and BACK to the one before, and what cannot be undone asks first. What needs text is set from the web page. `About` is what the device is, on two pages that OK turns between. The first page shows the wordmark, build version, project QR code, author and license; it is the splash too. The build version is supplied verbatim by `APP_VERSION`, or derived from `VERSION` with a commit suffix when Git information is available. The second is the device's state - its name, its network and address, the firmware version, free RAM, free flash for applications and free room of their stores, and uptime. Device information comes from `sys_info`; uptime is calculated from `time_uptime_ms()`.

What stays native is what has to work when nothing else does: the menu, the message of an application that crashed, the question about a storage that cannot be read and the question a request from the network waits on. The screen that says how to give the device a network is a system application too (`setup`, not in the menu): without it the device starts at the menu, and About has the address. The splash at power-up is not among them: it is About's picture, and without it the device simply starts.

They are written with the **system API**, the `sys_*` part of `sdk/host_api.h` (`sys_info`: the version, the name, the network and its state, the address, the slot, what is free of RAM, of the flash for applications and of their stores; `sys_setting_get` / `sys_setting_set` / `sys_setting_range`: only the explicit page-visible keys documented in `sdk/host/sys.h`, with internal and unknown keys returning `HOST_ERR_NOT_FOUND` for all three calls; `sys_time_set`; `sys_app_list`, `sys_app_title` / `sys_app_remove` (HOST_OK queues one removal after the handler returns; a second returns HOST_ERR_NO_SPACE); `sys_app_get_default` / `sys_app_set_default`; `sys_run`: restart, forget the network - Wi-Fi is then off - factory reset, and since 0.1.66 `SYS_DO_WIFI_SETUP`, Wi-Fi on again with the setup access point; `sys_draw_logo`, `sys_logo_width` / `sys_logo_height`). It is not fenced off: the device is its owner's, and any application may have it. It has to ask - `"system": true` in its manifest - and the page says "<title> requests system access." before it installs one. A module that imports a `sys_*` call without having asked is refused by the build (`tools/perinkpheral build`) and by Perinkpheral OS.

### Execution model
- **Scene** - one application, it owns the screen and the buttons.
- **Polling** - Perinkpheral OS schedules every compatible installed application's polls using the resolved interval, with a minimum of 300 seconds while power saving is active. The next ordinary deadline is scheduled after the current poll round finishes. Polls are requested after startup, by `poll_run`, and after saving the application's settings. Obtaining a network address immediately requests polls whose last attempt failed in transport (no network, connection, DNS, TLS handshake, timeout or interrupted body), in every power profile, together with polls already due. A connection never brings healthy polls forward. HTTP refusals, including 429, invalid answers, untrusted certificates and local preparation or memory failures keep their normal pace; applications own their server cooldowns. Retries coalesce with pending work and preserve deferred `poll_run` deadlines. A transport failure ends an `each` round; reconnect starts one new round, not one retry per failed item. It adds no wake-up. Raw requests still waiting in the bounded queue proceed; an already failed raw request is never replayed. Methods that change server state must tolerate these repeated sends.
- **A poll over a list** (the owner, 2026-11-15: "one common list"): `"each": "<list setting key>"` sends one request per item, one at a time between other work. `answer_item()` identifies it. A `prefix` poll claims matching items and substitutes them without the prefix in the URL, headers and body; a poll without a prefix takes the items no prefixed poll claims. Up to 16 requests per application may wait in the queue.
- **Queued credentials and destinations** - a raw request's expanded URL is queued unchanged. Immediately before sending, the main event loop reauthorizes it against current application KV values and fills its headers in that same operation, with no settings save or application write interleaved. A changed url/link setting can make the old destination fail with `HOST_FAILED_NOT_ALLOWED`; it is never silently retargeted. Scheduled manifest polls instead expand their URL, headers and body at dispatch and do not use the `hosts` allowlist. Once prepared, either kind of request keeps that snapshot through transmission. Templates read any application KV key, including undeclared ones, with manifest defaults for absent declared settings. In a poll URL, header or body, `{{` always opens a store key of 1-15 characters from `!` to `~`, closed by `}}`; the build refuses invalid keys or unclosed placeholders, and a literal "{{" cannot be sent.
- **Raw requests** - an application may itself call `http_send` (method, URL, headers, body) - for OAuth, calendars, actions on a button. Requests go into Perinkpheral OS's queue, one at a time for the device; an application has up to 16 waiting (`HOST_HTTP_PENDING_MAX`) and queues more as answers come, the applications taking turns and polls taking turns with requests; the queue lives on the heap, 16 KB at most for the device, including records, URLs, headers and bodies. Raw-request tags are 16-255, the URL is at most 511 bytes, header text at most 1023 bytes and the binary body at most 512 bytes. Headers contain at most four fields, with names up to 31 bytes and values up to 255 bytes. Raw body bytes are copied at queue time and are not template-expanded; scheduled polls wait as schedule entries and allocate their body only for the active request. Only hosts from the manifest's `hosts` are allowed. The response arrives through the same `app_on_data`; an interrupted one is dropped, not repeated.
- **Redirects** - a `GET` that is answered with one is asked again where it says, up to three times. GET polls follow redirects even to hosts outside `hosts`. A poll of any other method delivers its redirect response without replaying the request. A raw GET redirect to the same name with the same port, or with both ports in {80, 443}, bypasses the allowlist check. Other redirect destinations must be in `hosts` or fail with `HOST_FAILED_NOT_ALLOWED`. A change of host or a downgrade from HTTPS to HTTP drops application headers for the remaining hops, even after an earlier upgrade. A request of another method is not sent twice: its redirect is the answer.
- **Delivery** - Perinkpheral OS calls `app_on_data(request, ptr, len, flags, http_status)` in chunks (flags: FIRST, LAST, FAILED; the HTTP status comes with the first chunk) on the owning application, **whether it is on the scene or not**:
  - on the scene - the call is made right away;
  - not on the scene - unload the scene (`app_on_blur`) → load the owner → deliver → if it called `screen_request()` it is opened as the scene - anew, from what it stored - otherwise unload it and bring the previous scene back (`app_on_focus`).
- **Install and update notifications** - loading must succeed before the notification is consumed, then it is consumed before its callback, including a missing or trapping callback and an instance stopped by `app_on_load`. A load failure stays pending until the next startup or application-list reload. "Updated" means a different module-and-manifest package id, regardless of version strings.
- **State** - Every application must restore itself from `kv_*`: Perinkpheral OS unloads it on every scene change and background delivery. **Where the user is** - a page, a row, a value half set - is not worth a write of the flash and goes into the session (`session_set` / `session_get`, up to 1024 bytes of RAM allocated when first set, held by the scene; the one mechanism since 0.1.61 - `scene_state_*` was removed, and an application that keeps more than 128 bytes names firmware 0.1.61): kept while the application is in the stack, across its unloads, and gone when it leaves the stack (BACK from its first page, `screen_leave`, a long BACK, too many above it), when it is opened anew from the menu, and at a restart. Saved in `app_on_blur`, read in `app_on_focus`; an instance loaded off the screen only reads it. `app_session_save` / `app_session_load` in `sdk/lib/app_state.h` keep one struct that way. Settings, Calendar and HA keep theirs. The displayed image stays while the scene is suspended; resume schedules a redraw, and an identical frame causes no panel refresh; an application's timers (`timer_set`) stop when it leaves the screen and are set again by it in `app_on_focus`.
- **Buttons** - the layout is the same everywhere in Perinkpheral OS: 1 up, 2 ok, 3 down, 4 back. Applications are encouraged to keep it.
- **Navigation uses a stack** (`firmware/components/ui/wm.c`, pure). The menu is under everything and is what shows when the stack is empty. A long press on BACK is the beginning again: the stack is emptied and the menu shows, and BACK in the menu does nothing - unless the user chose a default application, which BACK in the menu then opens. Whatever takes the screen goes on top - an application opened from the menu, a question Perinkpheral OS asks, an application whose alarm came - and the one under it leaves and waits; when the top is done, what was under it enters again. BACK is one step down. Opening from the menu starts anew; a scene is in the stack once - opened again, it moves to the top from where it waited; six deep, the oldest forgotten. Only the top is loaded - there is room for one application - so a scene that waits enters again from what it stored. Nobody keeps a "where to return" of their own: Perinkpheral OS's question and its work notice are entries like any other. **BACK is the way out and needs no code**: a short press of BACK leaves an application that does not export `app_on_back()` - to the menu, when it was opened there. One with pages of its own exports `app_on_back()`, gets the press there instead of in `app_on_button`, goes a page back and calls `screen_leave()` from its first. Normally `screen_leave()` is one step down, and one that took the screen with `screen_request()` returns the user to what they were looking at. After BACK+UP/DOWN switching, leaving an application in that sibling row clears the entire stack and its sessions and returns to the menu.
- **Switching without the menu** (the owner, 2026-11-20): button 4 held and button 1 or 3 pressed opens the previous or the next application in the menu's order, round its ends, the system's pages passed over (`components/ui/back_switch.c`, pure; `scene_menu_neighbour`). Not in the menu: it is the list itself, and its UP and DOWN choose a row. **The neighbour is opened beside, not anew** (`wm_open_beside`; the owner, 2026-11-20, at the same acceptance, where Life came back from a switch at generation 0): the application switched from waits in the stack with its session, so the way back finds it as it was - up to the stack's six, the oldest forgotten; a short BACK from any of such a row is the menu, never the neighbour, and ends them all. Opening from the menu is still a start anew. It acts on the way down. The chord's UP or DOWN events are consumed. The application may already have received BACK KEYDOWN; after a chord, it receives no further event for that BACK hold. Sibling switching preserves the previous application's session. **The long BACK acts when the button is let go** (the owner, 2026-11-20, at the acceptance of 0.1.63, where it acted at 600 ms and took the menu's way before a second finger reached UP or DOWN): a hold of any length can become a chord, and a hold that switched ends in nothing. A long press with no button down - a tool's - acts at once. No application loses a handler: the long BACK was never theirs.
- **Switching** - long press on button 4 → Perinkpheral OS menu (list of applications, selection with buttons 1/3, confirmation with 2, button 4 opens the default application when there is one). A row of the menu is the application's icon and its title; the selected row is inverted, white on a black bar. **The menu's order is the user's** (the owner, 2026-11-16): a long press of OK takes the row to move - it stands in a frame, and along the bottom UP and DOWN at the sides and OK in the middle, the kit's own buttons with no words - UP and DOWN carry it a row and stop at the ends, OK keeps the order, and BACK, which the row does not name, puts the row back, as a long BACK does - in the menu the long press is the menu's own; whatever takes the screen meanwhile puts it back too. Every row moves, Settings and About among them. The order is kept by name in Perinkpheral OS's settings (`menu_order`, `menu_order.c`, pure), an application installed since comes first - one removed forgets its place, so it comes first when it is back - and the page shows its tiles in the same order. All other button events go to the application on the scene.
- **Preemption** - `screen_request()` from an application that received data in the background. Protection against a war for the screen: no more than one preemption per N seconds (30), whoever asks - there is no priority between applications; none within 30 seconds of a press of the user's, and none over a question waiting for its answer (what cannot wait is a `notification_post`); the decision is made after delivery ends, after the last piece of a streamed answer, and a refused request is discarded without retry; a long press on button 4 always returns control to the user, and the notices that wait show at the next press, not over the menu at once.

### Perinkpheral OS architecture
Perinkpheral OS is organized in layers. Each layer knows only the ones below it:

| Layer | Where | What it does |
|---|---|---|
| Drivers | `firmware/components/epd` (`epd.c`), `firmware/components/input`, `firmware/components/board` | the panel, the buttons, the antenna switch |
| Display service | `firmware/components/epd` (`display.c`, `refresh_policy.c`) | keeps a copy of the frame the panel shows; given a new frame it leaves the panel alone if nothing changed, refreshes it, or says "too soon" |
| Graphics | `firmware/components/gfx` | draws on a surface: the whole frame or a viewport into it with its own origin and clipping |
| Maps | `firmware/components/map` | the land of the Earth and its projections, drawn on a gfx surface; main firmware only |
| Window manager | `firmware/components/ui` (`wm.c`) | which scene has the screen, how the user moves between scenes, how a frame is put together from the header and the scene's picture |
| Scenes | `firmware/main/scene_*.c`, `firmware/components/appsys/app_scene.c` | tie a model to a view and decide what the buttons do, all behind one interface (`scene.h`): enter, leave, button, draw |
| Views | `firmware/main/screens.c` | a struct in, pixels out; no hardware, rendered by `tools/preview` |
| Services | `firmware/main/sysinfo.c`, `firmware/main/status.c`, the settings' store, the poller (`firmware/main/poller.c`), `firmware/components/net` (Wi-Fi, the clock) | the data, with no idea that a screen exists |

- **A partial refresh sends only what changed.** The display service finds the box outside which the new frame is the frame on the panel (`frame_box.c`, pure) and the driver sends that window - Waveshare's own `PartialDisplay`, the same commands and waveform. The window is taken together with the one of the refresh before, so that the result does not depend on what the controller does with its two frames afterwards. After a partial refresh the panel is left out of deep sleep for 1.5 s (a deadline of the main event loop's puts it there), and one that comes in that time needs no reset. Partial refresh duration depends on the transferred window and panel BUSY time.
- **A list stands still while the selection moves inside it** (`list_first_row`): its top row is kept - by the menu, by Settings for each page, by `app_list_first` for an application - and moves only as far as the selection needs to be seen, so a step does not move every label on a panel that takes half a second to show it. **A long UP or DOWN moves a page** of rows and stops at the ends, in the menu, in Settings and in `app_list_button`; in the date editor it steps a part far (minutes by ten, days by a week).
- **A list longer than the screen has a scroll bar** at its right edge (`firmware/components/ui/scrollbar.c`, pure): a thin line and a thumb on it - as much of the line as the rows shown are of the list, as far down as the first of them. The selected row is shorter by the bar's room. Perinkpheral OS's menu has it, and the lists of Settings draw the same. **A row's label and value never meet** (`list.c`): too wide together, a value of up to half the row - a time, a state - stays whole and the label is cut with `...`; a longer value has what the label leaves and never less than the half.
- **Two frames.** The back buffer (`host.c`) is where frames are put together; the display service holds the front copy of what the panel shows. Drawing never touches the panel, an unchanged frame costs no refresh, and a scene cannot spoil the screen halfway.
- **Layers are areas of one frame**, not buffers of their own: the header and the content do not overlap. A scene that is not full-screen gets a viewport under the header and cannot draw outside it.
- **A scene never refreshes anything.** It reports that its picture changed and draws when asked; the window manager passes on why the frame changed (a switch, a press, data), and the display service decides what the panel does.
- **One module keeps shared deadlines** (`firmware/components/deadlines`; OTA probation, button debounce and network request timeouts keep their own timing): the scene's timers, the applications' alarms and polls, the panel's sleep and its daily refresh, the while after a press, Wi-Fi's retries, the day turning in the header, the menu left idle, the device stopping. The table is pure (`deadline_table.c`); around it are one timer set for the nearest and the clock as the scale. Due deadlines are posted to the event queue and handled by the main event loop. If posting fails, the deadline remains due.
- **One event loop** (`events.c`). A press, later a timer or a response from the network, is posted from its own task and taken off by the main event loop one at a time: application handlers and scene changes are serialized in that loop. Service tasks run concurrently with published snapshots and their own locks.
- **The menu is a scene** like any other, not a layer over an application: opening it clears the navigation stack and its sessions, taking the screen away from whatever had it.
- **Priorities** (the model of 2026-11-14; in code it is one header, `firmware/components/board/include/priorities.h`, which every task takes its number from and which will not compile with the tiers out of order; a number is a FreeRTOS priority, the larger the sooner). What the user sees and touches comes before what is computed for them, and what keeps the radio alive comes before both:

  | Tier | Who | Priority | Why there |
  |---|---|---|---|
  | The radio and the network | Wi-Fi 23, the timer's task 22, system events 20, TCP/IP 18 - ESP-IDF's, not ours to move | 18-23 | late, they lose the connection |
  | Input | `buttons` | 10 | samples the pins for milliseconds; a press must be seen whatever else runs |
  | The screen | the main event loop (`host_run`, the main task) | 6 | draws the panel, runs the applications' handlers, answers presses |
  | Servers | the web server 5, `wifi` (the plan of connecting) 5 | 5 | a person may be waiting at a browser, but not at the device |
  | Background | `poller` 4, `ota-probation` 4, `captive_dns` 4 | 4 | a TLS handshake is seconds of arithmetic nobody watches |
  | The rest | the development console 2, mDNS 1, FreeRTOS timers 1, idle 0 | 0-2 | |

  Rules: a task that only computes goes under the main event loop; a new task is given its tier here before it is written; nothing of ours goes above 10.
  **Interrupts** are all of one level (1): the buttons' pins, the timer, the radio. A handler of ours does nothing but hand on - a semaphore, a count - and the one that counts the ten seconds of the rescue combination touches RAM only. Above them is the interrupt watchdog alone (300 ms). No critical section of ours is longer than the panel's reset pulse, 2 ms.
  **Events** have two queues, and the main event loop takes input first: presses (16 slots, four reserved for releases) before everything other tasks ask of it (64). The others ask one thing at a time and wait for the answer, so nothing piles up before a press but the one call in hand; what a press does wait for is what the loop is in the middle of - a handler (a cooperative 3000 ms execution budget, checked at interpreter yield points, after native imports and on return; native calls and scheduling delays can extend elapsed time), a refresh (0.5 s, or 2.2 s for a full one).
- **Development tools** (`APP_DEV_CONSOLE`, on by default, off for a release): the device is driven and looked at without hands on it. Over the network, `/api/dev` takes presses, opens an application and takes a new build of one; `tools/perinkpheral` is the command line for it, and `tools/perinkpheral run <app dir>` builds an application, uploads it, restarts the device and opens it without reflashing. `tools/perinkpheral serve <app dir>` is the same for a person in a browser tab beside any editor - the live screen, the four buttons (and the keyboard's arrows, Enter and Backspace), the log as it is written and a Run button; `tools/perinkpheral new <name> --author "Your name"` makes an application to start from, and `log --follow` prints the log as it grows (`/api/log?since=<where the last answer ended>`, the end in `X-Log-End`), on across a restart: a device that was away is asked when it started, and its new log is read from the beginning. The page of `serve` takes requests from itself only, as the device's does: another site in the same browser could otherwise press the device's buttons through it. `tools/perinkpheral build` says what a build came to against what the device has: the module, the code and the estimate of what running it takes, the memory of its stack and data, both together against the 112 KB area, the files. Over the cable, characters typed into the USB console do the same for a device with no network (`tools/perinkpheral usb <port>`). Whatever touches the frame or the scenes is handed to the main event loop through the event queue.

### Perinkpheral OS screens: notices
Native confirmation, storage-error and working scenes use the full screen without a header. Notifications retain the header; application notices use their application's drawing surface. `notice_draw` (`firmware/components/ui/notice.c`, pure) supports one or two main lines, an optional icon, optional detail text and either button actions or three static working strokes. Main text uses a smaller font when needed to fit. No bar that moves. **The buttons are named the same way everywhere** (`kit_actions`): a button's name white on black - what OK does and then OK from the left edge, BACK and then what it does from the right: `Format OK        BACK Skip`. A button that is the only one stands in the middle. The icon stands a little in from the right edge.
- **A question** (`scene_confirm.c`): "Factory reset?" with the warning icon, "Join <network>?" with the signal, "Install system app?" with the gear. OK confirms; BACK or opening the menu cancels. An unanswered main-firmware question expires 60 seconds after it opens; other button activity does not extend that deadline. A press is not an answer until the question is on the panel. Recovery draws and handles the firmware-update confirmation.
- **An error** (`scene_storage.c`): "Storage" / "error" with the warning icon; OK formats, BACK continues without formatting.
- **Firmware update work** (`recovery/main/screen.c`): after physical confirmation, recovery shows "Updating" / "in progress" and "Keep the device on" while writing, then "Starting" / "Perinkpheral OS" before restarting. Recovery ignores buttons during these states. Main's `scene_working.c` provides a generic full-screen working notice.
- **A notification** (`scene_notify.c`, `notification_post` in the contract): what an application has to tell wherever the user has gone - the timer's "Time is up", the calendar's meeting that begins. The application hands Perinkpheral OS the notice from any handler, an alarm's above all, and is done: Perinkpheral OS shows it under the header over whatever has the screen, keeps it until a short OK or BACK dismisses it, and gives the screen back. At most four notifications are retained, including the displayed notification. Long BACK returns to the menu, discards the displayed notification and holds remaining notifications until the next press. A restart clears the queue.
- **An application that is not running** (`app_scene.c`): its title, "crashed" or "cannot start", why in a line of ordinary text under them ("App memory unavailable." when the boot reservation failed), the warning; a short press of any button closes it.
- **The questions Settings asks** - remove an application, forget the network, factory reset - are the same notice, drawn by Perinkpheral OS for the application (`ui_draw_notice`), under its header: OK does it, BACK cancels.
- **The kit** (`firmware/components/ui/kit.c`, `list.c`, `notice.c`, all pure, rendered by `tools/preview`) is what every screen is put together from, Perinkpheral OS's and an application's alike - the design system. Primitives: text in four styles (text, title, caption, value), the title of a page with its line, an icon in three sizes (22, 44, 99 px), a button with what it does, the row of buttons along the bottom. Elements: a value bar that changes only with its data, a chart (a series of numbers as a line, an area, bars or steps), the frame with arrows around what UP and DOWN change. The cell - a name, a picture and a value in a box of any size, which is what a dashboard is made of. Screens: the list (rows with values, options with a check, facts nobody chooses from), the notice (a question, an error, work going on, a message such as "Not set up"), the picker of one value from a row, the date and time set a part at a time. An application asks for them with `ui_*`; **what the buttons do on those screens is `sdk/lib/app_ui.h`** (`app_list_button`, `app_picker_button`, `app_date_button`, each answering changed, done or cancelled), so an application writes only what the result is for. Nobody has to use any of it: `gfx_*` draws anything. Settings is written with it, and `kit` in the catalog shows every part on a page of its own.
- **Any application may ask for Perinkpheral OS's look**: `ui_draw_notice` is this notice, and `ui_draw_list_row` a row of Perinkpheral OS's list - the bar behind the chosen row, a value or an icon at the right edge, the scroll bar (`firmware/components/ui/list.c`, pure). The menu and the lists of Settings are drawn by the same code, so an application that uses it looks the part and stays so when the look changes.

### Power-up
A partition of applications that cannot be read is not formatted without user confirmation: after the splash the device says "Storage" and "error" with Format and Skip (`scene_storage.c`, native - it has to work when nothing else does). Skip leaves the device running with no installed applications; Format erases the partition and restarts. What the applications stored is in NVS and stays.

The splash initially waits six seconds or a short press. Background delivery cancels its timer; when the splash resumes, it schedules its transition after 1 ms:
- **no network stored, Wi-Fi not turned off** - to the setup screen: the name of its access point and the address to open;
- **otherwise** - with a network, or with Wi-Fi off - to the one-use application selected by development tools, then the installed default application, then the application that was on the screen last (its name is kept in NVS), or to the menu when there was none.

A device on a shelf has to come back from a restart showing what it showed, without a press.

**The default application** (`default_app` in the settings, by name; Appearance in Settings on the device, and on the page) is what the device shows by itself: after a restart, by BACK in the menu, and when the menu has been left alone for `menu_idle_min` minutes (1 to 60, 5 by default; `DEADLINE_MENU_IDLE`, set anew by every press). Only the menu gives way: an application that took the screen - by an alarm, say - has something to tell and stays until the user closes it. A default that is not installed is as none.

### Wi-Fi
- **No network stored** - a device never set up, or after a factory reset - the device starts an open access point named after itself (`Perinkpheral-XXXX`) and waits to be set up at `192.168.4.1`. The setup screen shows a QR code that joins a phone to that access point, with the network name and the address in words under it. A QR code cannot both join a network and open a page, so the access point is a captive portal: its name server (`captive_dns.c`) answers every name with the device, the web server redirects whatever it does not know to its page, and the phone may offer the setup page; the access point's DHCP lease names the page too (option 114, RFC 8910), for a phone that reads it. Otherwise, open `http://192.168.4.1`. The name server answers only while the access point is up.
- **A network stored** - it connects; after connection loss it retries immediately. Failed attempts then wait 2, 4, 8 ... at most 30 seconds.
- **Wi-Fi off** (the owner, 2026-11-20: "I may want to turn Wi-Fi off and look at the clock"): forgetting the network - Forget network in Settings on the device, `SYS_DO_FORGET_NETWORK`, `POST /api/wifi` with an empty `ssid` - leaves no network stored and `wifi_off` set in the settings. The device then starts where it starts with a network, with no access point and no name server; the Wi-Fi driver is not started at all (`WIFI_PHASE_OFF`), only the network stack, so nothing that opens a socket faults. The header's icon is struck through, applications get "No network", the device's name is not announced, the clock runs and is set by hand. Settings > Wi-Fi shows Status Off and one action, **Connect to Wi-Fi** (`SYS_DO_WIFI_SETUP`): the device restarts with its setup access point and the setup screen, as a new one. The two are ABI 3 additions of 0.1.66, approved by the owner on 2026-11-20 inside the freeze: `SYS_WIFI_OFF`, what `sys_info(SYS_INFO_WIFI)` says then, and `SYS_DO_WIFI_SETUP`; `SYS_DO_FORGET_NETWORK` changed what it does inside ABI 3 - before 0.1.66 it always answered `HOST_OK` and restarted into the setup access point; since then it turns Wi-Fi off, and with no network stored answers `HOST_ERR_NOT_FOUND` without a restart. An application built before sees both; the owner allowed it before the public release, and `sdk/abi/3.txt`, which records constants and not behaviour, does not show it. Over the page's API an empty network name asks "Forget network?" on the device, not "Join ?". A network joined through the portal ends the state. `wifi_off` is set only along with the network (`appconf_follow_network`), is read-only on the page and closed to applications; a stored network comes before it, so a network stored by an older firmware is joined. A firmware on probation with Wi-Fi off is confirmed after 20 seconds: its next update comes through recovery, entered with BACK at reset.
- **Two minutes without success** - rescue: the setup access point comes up as well and the device keeps trying once a minute, so a wrong password never needs the cable. Connected again, the access point goes away.
- The rules are `firmware/components/net/wifi_plan.c`, pure and host-tested; `wifi.c` only carries them out. The Wi-Fi library keeps nothing in flash: the credentials are Perinkpheral OS's settings.
- The default mDNS hostname is `perinkpheral-xxxx.local`. A custom device name produces a corresponding hostname, applied after restart. While reachable, the device announces `<hostname>.local` and its page as `_http._tcp` (`espressif/mdns`). During power saving, announcement is available in the two-minute user-awake window after startup or a press. It is disabled with Wi-Fi off.
- With `time_auto` enabled, each Wi-Fi connection requests SNTP synchronization. With automatic time disabled, the user can set the clock manually. The time zone is a POSIX TZ string in the settings. Everything a person reads is local time: the header, the status page and the applications through `time_zone_offset()`. `time_now()` returns 0 while the current clock is outside the supported time range; the header's time field is blank then.

### Header
Perinkpheral OS draws a header above its own screens and above every application that does not ask for the full screen:
- On the left the Wi-Fi icon in one of two states - connected, or not connected (the same icon struck through). It shows whether Wi-Fi has joined a network and obtained an address. A single server's TLS, HTTP or response failure does not change it; the application reports that failure. While the radio is off to save power, it keeps the outcome of the last Wi-Fi connection attempt. No extra connectivity requests are made for the icon.
- On the right the date (`Wed 11 Nov`), blank while the time is unknown.
- No application title or network name is added by Perinkpheral OS. The date changes once a day. There is no footer. **The time instead of the date** is a setting (`header_clock`, on by default since 2026-11-17; Appearance in Settings on the device, and on the page): the header then turns with every minute, above every application.
- **An application may put its own text into both**: beside the icon on the left, where Perinkpheral OS has nothing, and on the right in place of the date (`header_set_text`). It gives a line and nothing more - the font and the size are Perinkpheral OS's. A text that does not fit is cut with `...`, and the two never meet: when together they are too wide each is sure of half the width, and what one does not need of its half goes to the other (`wm_header_share`, `gfx_fit_text`). A side the application gave nothing for is Perinkpheral OS's; a text of one space leaves it empty. The texts are forgotten when the application leaves the screen. `weather` shows its city, behind a setting of its own.
- **An application may keep an icon and a line in the header while it is away** (`header_set_status`): something the user set going and wants in sight - the timer's minutes left and its hourglass. The header reads **icon text ... text icon**: on the left the icon stands in place of Perinkpheral OS's Wi-Fi one with the line after it, on the right the line stands in place of the date with the icon after it. They are there above every screen with a header, whoever is on it. A side belongs to the package ID that last set it, until its owner releases it, the package ID disappears through removal or update, or the device restarts; a side kept this way comes before what the application on the screen gave for it - on the right; the left says where the user is, and a page's own title there comes first, the kept status showing where the screen leaves the side to Perinkpheral OS. A recurring alarm (`alarm_set_every`) is what keeps the line right. `timer` keeps the right side.
- An application chooses in its manifest: `"fullscreen": false` (the default) leaves it 400×260 under the header, with its coordinates starting there, and it cannot draw over the header; `"fullscreen": true` gives it the whole 400×300. A long press on button 4 opens the menu in either mode.
- The network name and the address are on the second page of About, not in the header.

### Perinkpheral OS API (wasm imports)
The only contract is `sdk/host_api.h`, written by subject in `sdk/host/` - `base` (the macros, the return codes, the log, `HOST_LAYOUT`), `app` (lifecycle handlers, settings, the session, intents), `buttons`, `text` (strings, `text_fill`), `gfx`, `ui` (the kit), `screen` (drawing a frame, redraw, the header, the stack, notifications), `net`, `store` (the store and files), `time` (with alarms and timers), `sys` - which the umbrella includes and the tools read in that order. An application includes the umbrella and no file of `host/`: which declaration stands in which file is not the contract (the owner, 2026-11-20) and may change after the freeze; an entry added after the 0.1.30 ABI floor has its `HOST_SINCE_` stamp beside it, and every struct that crosses the boundary is held to its size on both sides (`HOST_LAYOUT`). Applications and Perinkpheral OS's import table are built from it, and the build (`tools/perinkpheral build`) refuses a module that imports anything else. Existing ABI 3 names, signatures, privileges, constants, layouts and meanings stay available. `HOST_API_VERSION` and the manifest's `abi` are 3; a changed signature or meaning requires a new ABI. Additions carry permanent `HOST_SINCE_<name>` stamps and preserve recorded entries in `sdk/abi/3.txt`, with the `HOST_ICON_COUNT` exception described above. ABI 2 is refused without adapters; its applications must be rebuilt for ABI 3. Commands name the subject then the verb (`kv_get`, `gfx_draw_text`); queries name the subject and what is asked (`gfx_width`, `time_now`); events Perinkpheral OS calls are `app_on_<what happened>` (`app_on_load`, `app_on_picked`). **Perinkpheral OS's icons** (`firmware/components/gfx/icons`, `HOST_ICON_*`): 52, including navigation, notices, weather, home, energy, air quality (`PARTICLES`, `POLLEN`, `GAS`, `DUST`, `LEAF`, `MASK`), 3D printing (`LAYERS`), completion (`PROGRESS`, a partly filled pie) and boxes or volumes (`CUBE`, an isometric box: the hexagonal outline and the front Y, no hidden edges). LAYERS, PROGRESS and CUBE were added in 0.1.84. Each has an 11-cell drawing; optional 22- and 44-cell drawings supply finer detail. Perinkpheral OS uses the finest drawing that fits at two pixels per cell or more, except UPDATE (the project mark), which always uses its original 11-cell drawing. `gfx_icon_ink` measures the visible ink. `tools/perinkpheral icons` makes `gfx_icon_art.c`; `preview` makes the three icon sheets used by the guide. Symmetric icon subjects and parts must be exactly mirror-symmetric about their axes at 11, 22 and 44 cells, with the axis on the middle cell at 11 and between the middle cells on even grids; only details that carry meaning may be asymmetric.

**As many applications as the device holds** (the owner, 2026-11-16): at most 24 installed, each with a guaranteed 2 KB store. A module is at most 48 KB and occupies whole sectors of `appcode`. Files are counted in 4 KB blocks. A read-only package may bring 64 KB; `"writes_files": true` reserves 32 KB for its files, including packaged data. The build and Perinkpheral OS require that privilege for `file_write`. Installation checks the installed-application limit, code capacity, staged filesystem space, existing writer reservations and 13 spare filesystem blocks (`app_install.c`, using `app_room.c`). After manifest validation it checks the writer quota, including manifest blocks, and checks it again before commit. `flash_budget.c` guarantees aggregate KV-store capacity at compile time. `/api/status` reports storage use.

**Put off: BLE** (the owner, 2026-11-13). The C6 has BLE 5, no classic Bluetooth. A Perinkpheral OS service for media keys would own pairing and bonds; applications would request its roles. Measure flash and heap cost beside TLS before adding it. No BLE service is implemented.

**How soon a redraw is shown** follows from where it was asked: from `app_on_button` at once, from `app_on_timer` and `app_on_data` by the e-paper policy. Flags on `screen_redraw`: `HOST_REDRAW_SOON` - bypass the data interval with a one-second minimum; `HOST_REDRAW_CLEAN` - a full refresh, for a new picture; `HOST_REDRAW_NO_BLINK` - now, and not as the full refresh Perinkpheral OS makes after every few partial ones: for pictures in a row; `HOST_REDRAW_QUESTION` - the picture asks what OK answers: OK reaches the application only when it went down after that picture was on the panel, as Perinkpheral OS's own questions take theirs (`scene_t.question`, `is_press_for` in `host.c`). With NO_BLINK, ghosting accumulates until a full refresh. Applications have no redraw quota. Frequent refreshes consume energy and increase panel wear. SOON and CLEAN wait until one second after the preceding refresh. NO_BLINK has no minimum interval and suppresses periodic full refreshes. Button refreshes use the configured button interval; data refreshes use the configured data interval. Initial frames and scene switches require full refresh, with no additional interval delay.

What a handler may count on: one handler runs at a time with a cooperative 3000 ms execution budget. The runtime checks it at interpreter yield points, after native imports and on return; native calls and scheduling delays can extend elapsed time. Event handlers return no value; `app_data_buffer` and `app_strings_buffer` return application-memory pointers. Redraw and focus requests are processed after handlers return. `screen_leave()` takes effect after `app_on_button`, `app_on_back` or `app_on_timer` returns and is ignored in other handlers; input has sixteen event slots, four reserved for releases; new non-release events are refused once twelve events are queued, timers of one id collapse into one, and the pieces of one answer arrive in order - a setting saved or an alarm may come between two of them.

There are no pointer callbacks. An application exports functions with fixed names (Perinkpheral OS skips the missing ones):
```
app_on_load()
app_on_focus() / app_on_blur()
app_on_terminate()                  // before unload, unless the instance has already stopped because of a fault: save here
app_on_installed() / app_on_updated() // once: new on the device (or removed and installed again), or a different module-and-manifest
                                    // package ID replaced the one that ran, regardless of version strings; told at startup and list reload
app_on_back()                       // a short press of BACK, for an application with pages of its own; without it BACK leaves
app_on_button(event)                // raw button events and interpreted UP, OK and DOWN events
                                    // BACK PRESSED goes to app_on_back or closes the application if that export is absent
                                    // BACK LONG_PRESSED is reserved for Perinkpheral OS; navigation holds may have no delivered KEYUP
app_on_timer(id)
app_on_draw()                       // paint the whole picture from the state
app_on_data(request, ptr, len, flags, http_status)   // a response chunk; request is the manifest poll index or the tag supplied to http_send
app_data_buffer() -> ptr            // where Perinkpheral OS puts that piece: 1 KB, sdk/lib has it ready
app_on_picked(request, http_status)  // a poll's picked values in one call: answer_value(i)
app_on_settings()                   // the user saved the settings
app_on_intent(type)                 // news it subscribed to in its manifest
app_on_alarm(id)                    // an alarm came, on the screen or off it
app_strings_buffer() -> ptr         // where Perinkpheral OS copies the strings of the device's language
```
- **An application draws only inside `app_on_draw()`.** Handlers change the state and call `screen_redraw()`; Perinkpheral OS calls `app_on_draw()` when it needs the frame, with a white surface, and the drawing calls answer with an error anywhere else (measuring text works anywhere). Perinkpheral OS puts the frame together, compares it with what the panel shows and decides whether and how the panel is refreshed - so there is no `gfx_flush` and an application cannot leave a half-drawn screen. CLEAN requests a full refresh; NO_BLINK suppresses periodic full refreshes. The display service decides whether and when a changed frame is shown.
- **Mistakes the build refuses** (`tools/perinkpheral build`, 2026-11-14): a function named like a handler that is none (`app_on_buton`), a call whose answer has nowhere to arrive (`timer_set` without `app_on_timer`, `alarm_set*` without `app_on_alarm`, `http_send` without `app_on_data`), a poll or intents of the manifest without their handler, drawing without `app_on_draw`, a string or a picture the code never names. A module that fails a check is removed.
- **What the contract promises of an ordinary application is checked of every non-system application** (the owner, 2026-11-21: "these are checks of particular applications now; they must become checks of the SDK"). `tools/perinkpheral app-check <folder> [--only <capability>] [--app <name>]` builds each application, skips `"system": true` applications (including their own tests), and compiles each remaining application's C for the computer, with the address and undefined-behaviour sanitizers, against the **stand-in host** (`sdk/check/standin.c`: every call an application imports, the system API apart) and runs the capability checks (`sdk/check/checks.c`), which know no application: **sessions** - back from an unload it shows the same picture and BACK leaves it in as many presses, opened anew it is on its first page, a restart is survived; **store** - every write within the limits, also with generated long values for text, secret, place, choice and list settings; other types keep their configured values, and this case is skipped with a note if the generated settings exceed the KV quota; nothing written anew for an unchanged answer or a visit that changed nothing (a value the store already holds is no write: NVS compares first), a refused write survived and saved when the same answer comes again; **timers** - late, twice, after the clock is set, set again in `app_on_focus()`, alarms set again in `app_on_updated()`; **network** - every answer whole, in pieces of 1, 7 and 1000 bytes, cut off without LAST together with the background instance that took it (`sdk/host/net.h`: on-screen instances can also be unloaded mid-answer), FAILED after pieces, every failure status, HTTP 503, 404 and 304, unchanged, off the screen; **drawing** - a frame from every state reached, no drawing call outside `app_on_draw()` and none the host refuses. Which apply is read off the module's imports and exports and the manifest. "The same" is the picture - what `app_on_draw()` asked the host to draw - with the clock held still, so an application that shows the time is no exception. The picture is what the panel would show: a frame drawn when the application took the screen or asked for one (`screen_redraw()`, an inversion), with the header around it. The checks use a fresh background instance for each modeled answer or event. Firmware retains a background instance across streamed chunks and may deliver another event for the same application into it before the stream ends (`app_delivery.c`); requests are filled, held to `hosts` and refused when they are queued, as `poller.c` does. An instance is a forked process: it starts with the memory a module starts with. What only an application knows lies beside it and is found by its place: `test/check.json` - a simulator scenario's `at`, `tz`, `store` and `mocks` - and `test/*.c`, its own tests of its own logic, each a program compiled with the same flags against the same host and reported as `logic`. Native C and not the simulator, because the sanitizers find what a wasm module hides inside its page and because a test of an application's own reaches its statics; the price is that the stand-in host is a second reading of the contract - its drawing calls record and do not draw, text is measured as Departure Mono, the zone's rules are its changes in the years around the time an application is checked at - so what the panel shows stays the simulator's to say (`sim-test`). Failure paths are checked as well (the owner, 2026-11-24): **sessions** refuses session allocation and requires reporting if resume state is lost; **store** refuses writes after responses and the last press of short/long button paths, unloads immediately and compares the shown picture after unload, unless the draw records or header contain a visible failure; unchanged answers also arrive a minute apart with Cache-Control headers; **timers** refuses alarm allocation, then permits it during 60 seconds of timer retries, requiring the schedule or a visible failure; **notices** compares due delivery with a full queue that later accepts, and with receipt writes refused after acceptance, on the screen and through fresh background instances, then replays and unloads to detect lost or duplicate notices; **network** generates truncated, wrongly typed, null, empty-list, missing-record, oversized-number and long-string HTTP 200 answers from the supplied mocks, substitutes oversized decimal tokens in other protocols for sanitizer safety, compares JSON mutations against the retained and failed-answer pictures, and observes requests through chains of 120- and 300-second Retry-After responses including unload/focus; **clock** crosses DST in Berlin, New York, Lord Howe and Auckland and year boundaries, comparing live and reloaded pictures. A declared `clock_probes` UTC event or floating local date is checked against date-aware HH:MM conversion in each zone, through `time_local_at()` or `time_from_local()`. `failure_text` declares custom visible errors; `exceptions` names a narrow check and a nonempty explanation, printed in the report (schema: `sdk/check/README.md`). A missing matching mock, due notice or event probe is reported as a coverage note, never evidence that its content was verified. The checks do not infer an event's identity, calendar semantics, provider ordering, completeness of statistics, layout quality, crash-safe exactly-once delivery or whether an alarm a restart cleared should be restored; those need declared inputs and application tests or simulator pictures. `sdk/check/apps/specimen` keeps the contract in every capability; the tools' test breaks a copy of it a line at a time and each break is caught.
- **Runtime diagnostics**: the runtime warns once per instance about a handler taking at least 400 ms. It also warns after more than 12 validated `kv_set` attempts in its tracked one-minute window. That counter includes unchanged, refused and failed writes and resets after a minute or when another application writes; it does not measure physical flash writes.
- **Drawing and refresh diagnostics**: drawing outside `app_on_draw()` logs a warning once per instance. The main event loop logs an informational message once per deferred frame when the refresh-policy wait exceeds two seconds.
- **The module is not trusted.** One that imports anything outside Perinkpheral OS API is refused before it runs. Every pointer and length it passes is checked against its memory before Perinkpheral OS touches it, and coordinates and sizes beyond a few thousand pixels are refused, so that no call can cost more than the surface is large. A handler has a cooperative 3000 ms execution budget, checked at interpreter yield points, after native imports and on return. Native calls and scheduling delays can extend elapsed time. An over-budget handler is stopped, and recursion is stopped before it runs through Perinkpheral OS's stack. A handler that traps or is stopped ends the application. A foreground failure shows an error screen; a background failure unloads the instance and restores the foreground.
- **Data arrives as values or in pieces.** `firmware/main/poller.c` fetches every poll of every compatible installed application when it is due, one request at a time, over HTTP and HTTPS. A poll with `"pick"` in the manifest is read to the end by Perinkpheral OS, the connection is closed, and the application gets the values in one `app_on_picked()` call, reading them with `answer_value()` (`sdk/lib/app_values.h` turns them into numbers and text). Any other answer goes to the application as it comes: Perinkpheral OS reads up to 1 KB, copies it into the buffer the application named with `app_data_buffer()` and calls `app_on_data()` - flags say first and last, the HTTP status comes with the first piece, and a streamed request failure produces a callback with `HOST_DATA_FAILED` and no data, possibly after earlier chunks that it invalidates, the status saying why: no network, no answer, a setting not set, a host not allowed, a timeout - an answer of values not read in a minute, of pieces in five, is one too -, a certificate the device does not trust, an answer over 256 KB (4 MB for one handed on in pieces: a calendar of some years is a megabyte or two), no memory. Either way an application that is not on the screen is loaded for the delivery and unloaded after it (`app_delivery.c`); a poll that cannot start at all - no network, no memory - is told only to an application on the screen. Request latency and peak heap use depend on the application, server, connection and firmware build.
- **State lives in the store.** An application is unloaded whenever it leaves the screen. Navigation and unfinished edits use `session_set` / `session_get`; the scene retains that RAM while it remains in the navigation stack. Persistent data that must survive a restart uses `kv_get` / `kv_set`: up to 1 KB per key and 2 KB for all the values of one application, its settings among them - counted as they lie in the storage, 64 bytes for a value and its length rounded up to 32, or many one-byte keys would fill the partition all applications share - keys of up to 15 characters, in the `appkv` partition. The namespace is `a.<name>` and an application's name cannot hold a dot, so no application can reach Perinkpheral OS's settings or another application's values. `hello` reads its count when it starts and saves it in `app_on_terminate()`.
- **Text is bytes, and what is not ASCII Perinkpheral OS draws as well as it can.** Perinkpheral OS hands on the UTF-8 of an answer as it came - a value picked from JSON is cut between characters, never inside one - and an application may store it and send it back. The fonts have ASCII only, and `gfx_fit_text` cuts between characters. What is beyond ASCII is drawn by Perinkpheral OS, the same in every application, down a ladder: the letter's own glyph from a **glyph pack** when one is there (`gfx_pack_add`; `tools/perinkpheral glyph-packs` makes `latin`, `cyrillic` and `greek` - pack sizes depend on the generated artifact: Departure Mono's letters as it has them; Jersey's Latin as it has it, 191 of the 232; Jersey's Cyrillic - every letter of the pack: Russian, Ukrainian, Belarusian, Serbian, Macedonian, Bulgarian, Kazakh - made by `tools/cli` (`JerseyCyrillic.kt`) from the Latin glyphs of the same face, mirrored, cut and joined, using the tested construction published on 2026-11-16, with isolated corrections to Ы/ы spacing and lowercase ь counters in Jersey 10, 15 and 25, and the lowercase б in Jersey 25 built from its Latin f hook and b bowl. The restored pack has Departure Mono and Jersey 10, 15 and 25, exactly the tested face set. Jersey 20 has no Cyrillic or extended Latin in this pack, so Cyrillic at the largest size falls back to ASCII spelling. Jersey has no Greek, which also falls back to spelling); else its spelling in ASCII by a table (`spelling.h`, made by `tools/perinkpheral spelling`: "Moskva", "Strasse", "Athina", a typist's dashes and quotes); else `?`. The degree sign (`\xC2\xB0`) is drawn in any font as a small square with a hole at the top of the capitals. On the device the packs live in a partition of their own (`glyphs`, 64 KB, mapped: `firmware/main/glyphs.c`), each in whole sectors, several side by side; a pack is written with its first bytes last, so one cut short by a loss of power is no pack. The user adds and removes them on the page (Settings, Language: the browser fetches a pack from the official catalog's `glyphs` folder and hands it to the device - `GET` / `POST /api/glyphs`, `POST /api/glyphs/remove?name=`), and the picture on the panel changes at once. Seen on the device: Russian, German and Greek in the calendar with the packs, spelled without. Departure Mono uses its Latin schwa for Kazakh; Jersey constructs it on each face's grid.
- **A complete answer has LAST.** Only `HOST_DATA_LAST` makes a streamed answer whole. `HOST_DATA_FAILED` may follow earlier pieces and invalidates all of them. Boundaries are unspecified, even inside a character or a marker. An interruption may end with neither LAST nor FAILED. **An answer may simply stop.** Response delivery can be interrupted on or off the screen. A button press, screen switch, application-list reload or delivery to another application can unload the receiving instance; the pieces still to come are dropped. An interrupted stream receives no additional completion callback. Foreground unload calls `app_on_blur()` and then `app_on_terminate()`; background unload calls `app_on_terminate()` without blur. An instance already stopped by a fault receives neither. A GET or HEAD poll cut off this way is fetched again in a minute, or sooner when its pace is shorter; polls of other methods keep their normal pace. Saving the application's settings also stops a poll stream: the instance may stay loaded, with no call to end the stream, and the poll is fetched again at once. An application keeps what it shows until an answer has come whole.
- **No floating point.** The interpreter is built without it - the chip has no FPU, and soft float in Perinkpheral OS was 34 KB - and without reference types, extended constants and compact imports; a module still has its one table of functions and calls through pointers. The build (`tools/perinkpheral build`) refuses an application whose code has a float operation and says which; one that got onto the device anyway stops when it reaches it. Numbers are integers - tenths, hundredths - and `sdk/lib/app_values.h` reads them that way.
- **No C library.** Applications are linked with `-nostdlib` against `sdk/lib`, a few hundred bytes of string building and the `memcpy` family, and `app_alloc.h` - an arena the application declares with `APP_ALLOC_ARENA(bytes)`, part of its data (`app_alloc`, and `app_alloc_mark` / `app_alloc_release` to give back to a mark); `printf` alone would take 16 KB. `hello` is 878 bytes.
- Time: with automatic time enabled, each Wi-Fi connection requests SNTP synchronization; otherwise the clock can be set manually. The time zone is a Perinkpheral OS setting.

### E-paper policy
Implemented in `firmware/components/epd/refresh_policy.c` (pure, host-tested). **The policy's numbers are user settings**: fields of Perinkpheral OS's settings with a range each, stored in NVS and followed by the display service: Display in Settings on the device, and Display on the page. The defaults start from Waveshare's recommendations for the 4.2" V2:
- data-driven updates (`app_on_data`, a timer, the clock) - no more often than once per **60 s**, counted from the start of the last such refresh, so that a clock can show minutes: what the user did in between - opened the application, pressed a button - does not put the next one off, and one that comes a second early is in time. Waveshare's own advice is 180 s and the panel is rated for a million refreshes; a user who wants the panel to last longer raises the number;
- reaction to a button - the user is looking at the device - **at once**, no pause by default; visible latency also includes the handler, event queue and panel refresh (measured at about half a second for a partial refresh);
- periodic full refreshes - **disabled** by default; the number of partial refreshes before one is a setting;
- at least one update per **24 hours** (a deadline of Perinkpheral OS's).

Fixed policy and rendering rules:
- The first refresh, every scene switch (including native notices), a due keep-alive refresh and a CLEAN request use full refresh. The keep-alive is due `refresh_keepalive_h` after the last full refresh, however many partial ones came between, and uses the normal waveform even with fast refresh on: a screen that changes every minute is still cleaned once a day. An unchanged frame is normally left on the panel.
- The panel goes to deep sleep (mode 1, RAM is kept) after every full refresh and 1.5 s after the last partial one, otherwise it degrades irreversibly. Its voltages are off after every refresh either way: the controller does that itself. The chip does not go into light sleep while the panel is awake, and the panel's lines keep their levels when it does (`gpio_sleep_sel_dis`).
- **Fast refresh** is a setting (`refresh_fast`, on by default since 2026-11-17, on the page): Waveshare's `Init_Fast`, its 1.5 s waveform. A full refresh measured 2.2 s with it and 2.7 s without. Disable Fast refresh for cold operation. The firmware does not measure ambient temperature or disable fast mode automatically.
- No animations and no real-time progress bars in Perinkpheral OS's own screens. An application that wants a row of pictures has `HOST_REDRAW_NO_BLINK`; the panel itself takes half a second for a partial refresh of the whole frame (0.41 s of it BUSY), and the application its time to draw, so that is three pictures in two seconds at best. `badapple`, removed from the catalog on 2026-11-20 for its video's rights, was the test: 200x150 unpacked and drawn in about 0.1 s a frame by the interpreter.
- 1 bit per pixel. Fonts are bitmap, pre-converted (`tools/perinkpheral font`), ASCII and the glyph packs; the readable minimum is ~10 px.

### Web UI (on the device, `esp_http_server`)
Main API requests require a Host naming the device's station address, setup address, hostname or `.local` hostname. If Origin is present, its authority must match Host. A failed check returns 403. Non-browser tools may omit Origin but must still use an allowed Host.

What exists:
- `GET /` - one gzip-compressed page assembled by `tools/perinkpheral page` from `firmware/main/web/`. It carries an `ETag` made of the image's hash and `Cache-Control: no-cache`: a browser asks every time and is answered `304` with no body while the firmware is the same (firmware 0.1.70; no `max-age`, or an old page would talk to a new API after an update). **Installed apps** lists applications with settings, information, Remove and compatible Update; **Update all** appears for at least two compatible updates. **Catalog** includes installed applications, marked Installed or Update, and uninstalled ones with Install; Refresh fetches the sources again. The sources dialog keeps the official source first and permits three added sources. **Device** shows status, restart, manual recovery entry and reset. **Firmware** shows the current build, releases with notes and custom image upload. **Log** follows entries and detects restarts. **Control** shows the frame and buttons in development builds only. **Settings** has General, Time, Display, Network, Language and Log. Time always shows date and time beside the Automatic toggle: on, it follows the device; off, it can be edited. The city or custom zone and the time server share one Save, which writes `/api/settings` and, for manual time, `/api/clock`. **Credits** lists the project, dependencies and fonts. The page uses the device's language. Its links include `#settings:time`, `#apps:weather` and `#apps:catalogs`. **A place that waits for the device says so one way** (`core.js`: `loadState`, `stateNote`; the owner, 2026-11-20: "a loading state must be added everywhere"): "Loading..." until the first answer, "Empty." for an answer with nothing in it, "Could not load." with Refresh for none; what was read once stays in sight while it is read again. The catalog as it was last read is kept in the browser without the lists of files and shown at once; until the sources answer it says it is loading and nothing is installed or updated from it. A dialog's buttons stay at its bottom edge when it is taller than the screen.
- `GET /api/settings` returns non-secret settings, including the saved SSID and Wi-Fi-off state. `POST /api/settings` updates ordinary settings: name, time, display, language, logging and power. Network credentials and Wi-Fi-off state use `/api/wifi`. Device name, NTP server and language changes require restart; the response reports "Saved. Restart to apply." Other supported changes take effect immediately.
- `POST /api/restart`.
- `GET /api/status` - name, firmware, slot, whether the image is on probation, Wi-Fi phase (`setup`, `connecting`, `online`, `rescue`; `off` exists for completeness - the page is not reachable then), network, address, free memory, configured `app_area` bytes, `app_area_available` (whether boot actually reserved the area), `app_area_used` (peak bytes since unload, 0 without an area), and why the device last started (`reset_reason`: 3 a restart asked for, 4 a fault, 5 the interrupt watchdog). After a fault `last_panic` is its record, kept in RTC memory through the restart (`firmware/main/crash_note.c`): how many starts ago, the reason, the task, the program counter and the code addresses found on the stack - `riscv32-esp-elf-addr2line -pfiaC -e build/perinkpheral.elf <addresses>` names the place.
- `GET /api/log` - up to the last 4 KB of captured ESP-IDF log text, without console colours. Individual captures are limited to 255 bytes; interrupt output and captures skipped during contention may appear only on the console. `X-Log-End` is where it ends, for `?since=`; `X-Log-Boot` is the run of the device it is of, another after every restart.
- `POST /api/wifi/scan` scans nearby networks and returns `{"networks":[{"ssid":"...","rssi":-60,"secured":true}]}`. It requires an allowed Host/Origin, memory admission and the shared waiting-handler slot. Busy or failed scans return 503. Settings > Network offers Scan networks and manual SSID entry.
- `POST /api/wifi` `{"ssid", "password"}` - validated like every setting, stored, and the device restarts to join. An empty `ssid` on a device with a network forgets it: Wi-Fi off, as from Settings on the device.
- `GET /api/apps` - the installed applications, each with its settings as the manifest declares them and their values (a secret only as set or not; another setting with nothing stored is left out, so the page tells a default from a value saved empty); `POST /api/apps/settings?app=<name>` `{"key": "value"}` - checked against the manifest, stored in the application's store, the application told (`app_on_settings()`) and its polls fetched again at once; `POST /api/apps/remove?app=<name>` - its files; the list of applications is read anew, with no restart; `GET /api/apps/removed` - the names of removed applications with retained stored values, up to 16 names; the response need not list every retained namespace. The page offers those first when adding one, marked "settings kept". The gear on an installed tile opens its visible settings; hidden keys remain writable through the API.
- `POST /api/clock` `{"unix"}` - the clock set by hand, as Settings on the device sets it, from 2026 to 2100, and only while the network's time is off.
- `POST /api/time` `{"tz"}` - the time zone, a POSIX TZ string; it takes effect at once, with no restart. The page works the string out from the browser's own zone and offers it; a device that was never told its zone gets it along with the Wi-Fi network, so setting the device up is one step.
- `POST /api/reset` - factory reset: the settings and the applications' stores are erased on the way up, and the device comes back with its setup access point. Installed applications, their filesystem data files and installed glyph packs are retained. The page has a button for it.
- `GET /api/screen` - the frame the panel shows, a 1-bit BMP in ink and paper, in every build (`web_screen.c`, apart from the development tools); `X-Frame` counts refreshes, `X-Pending` is 1 while a newer frame waits for the panel. The page's Device section saves it as a PNG screenshot; `tools/perinkpheral shot`, `serve` and the simulator read the same route.
- `/api/dev/...` - the development tools, only in a build with `APP_DEV_CONSOLE`: `POST button`, `POST open`, `POST app` (upload a file of an application), `POST run` (restart into an application), `POST flash` (409: use the recovery update protocol), `POST kv` (a value into an application's store), `POST restart`, `GET sockets` (every socket of the device and who is on the other end), `POST crash?kind=wdt|abort` (a deliberate fault, to test the record and the way back).
- The browser downloads releases from the existing GitHub Pages mirror before entering recovery. `/api/ota/release` returns 409: recovery has no HTTPS downloader. The flasher at https://perinkpheral.dev/flash reads `flash/index.json` from the firmware repository Pages. `tools/perinkpheral flash-manifest` generates first-install manifests, which carry `apps.bin` with the preinstalled applications (the flasher's fresh install erases the board and writes it), and data-preserving migration manifests, which do not (Keep data). Only the fresh-install manifest replaces IDF's blank `ota_data_initial.bin` at `0xf000` with the tools-generated `ota_data_first_install.bin`: sequence 1, state NEW and the bootloader's sequence-only CRC in the first journal entry; the rest of both sectors, including the recovery hint, stays erased. The second entry is erased as in an OTA selection from a blank journal, so it cannot retry a failed main. Keep data still writes the blank image.
- `POST /api/reset` and `/api/wifi` wait for Confirm on the device's own screen, a minute at most (see Open). They, `POST /api/apps/install` and `GET /api/catalog`, which wait for a download, run on a task of their own (`WEB_WAITS` in the table of routes): the web server has one task, and the page would hear nothing while one of them waits. One such request at a time; another meanwhile is "Device busy.".
- `POST /api/ota/recovery` selects recovery and restarts main. The page's **Device > Enter recovery** uses `?manual=true`, which skips the planned-update hint; without it, main records that an upload is expected. Recovery accepts a binary at `POST /api/ota`, checks its header before asking for physical OK, then writes only `ota_0`. Main refuses direct uploads with 409. `/api/status` distinguishes `mode: application` from `mode: recovery`, and reports `ota_protocol: 1`. Clients wait for the intended image identifier and completed probation, not merely a restarted HTTP server.

**Firmware over the network.** The upload is refused before a byte is written unless it is an image of this project (the image and description magic numbers and the project name) built for the partition table the device has. The new image starts on probation: it is confirmed only once the way the next update would arrive is open again - the web server is up and the device is on its network, or, with no network stored and Wi-Fi enabled, its setup access point is up and it has run for 20 seconds. Deliberately disabled Wi-Fi is an exception: with the web server up, 20 seconds of uptime confirms the image without network reachability; the next update requires entering recovery with BACK at reset. An image that has not got there within 3 minutes marks itself invalid, and the device restarts into recovery. There is no automatic return to the previous full firmware. The receiving (`ota_stream.c`) and the verdict (`ota_health.c`) are pure and host-tested; `recovery/main/ota.c` alone writes the main slot; `firmware/main/ota.c` selects recovery and confirms or rejects probation.
**Recovery contract (protocol 1).** Recovery is a separate ESP-IDF project in `recovery/`, built with every main firmware. Both use `firmware/partitions.csv`. Ordinary OTA never writes recovery, the bootloader or the partition table. Recovery reads `cfg/name`, `cfg/wssid`, `cfg/wpass` and `cfg/language` without repairing or erasing NVS. It always starts the open `perink-recovery` access point at `192.168.4.1`, and also tries the saved network when its credentials are usable. Its routes are only `/`, `GET /api/status` and `POST /api/ota`; main's settings, log and development routes do not run there. It does not load applications. The existing panel driver and antenna configuration are shared. The factory image must be selected durably, clearing both OTA journal copies, before main erasure begins; otherwise a stale VALID record may select the same failed sole OTA image again.

BACK held for three seconds at reset enters recovery through the standard bootloader. Only OTA metadata is cleared, never NVS or applications. A fresh USB install through the web flasher starts main automatically on probation, then shows its normal first screen: Wi-Fi setup with the QR code when no network is stored. No BACK press is required. The rollback-enabled bootloader changes NEW to PENDING_VERIFY; main confirms through the same health checks as an OTA update. A failed main returns to recovery. In recovery, BACK, labelled "Exit recovery", explicitly validates and tries the installed main with probation; a missing or damaged image cannot be started and needs another upload. Recovery never automatically retries a failed main. The 2026-11-18 hardware checks cover USB migration with byte-identical data partitions and successful OTA on the battery with USB absent. The owner cannot disconnect this device's battery, so controlled power-loss qualification remains pending on a suitable fixture; compiling, host tests and removing USB do not establish that behavior. Results and remaining cases are in `docs/testing/stability.md`.

Recovery uses Perinkpheral OS's `notice` and `kit` drawing, icons and English/Russian word tables. It reads the saved language and maps installed glyph packs read-only; absent or damaged packs fall back to ASCII spelling. NVS initialization itself uses a read-only partition descriptor, so IDF cannot repair the store during recovery startup. Confirmation shows the complete version, and network instructions are confined to the waiting/error screen. Updating, checking and restarting use the same working notice as main.

An intentional update carries a one-use UI hint: after selecting factory, main writes an eight-byte magic/complement pair at offset 64 of `otadata`, outside IDF's two boot records. Recovery consumes it before networking and accepts it only after a software reset. It does not affect boot selection, image validation or physical consent. Missing, unreadable or unconsumable hints mean recovery, never an assumed update. The requested-update path keeps one "Preparing update" screen while Wi-Fi connects and the header arrives, then asks for confirmation. Only a stalled handoff (30 seconds) exposes network instructions. Manual entry, failed probation and restarts after interrupted writes show recovery immediately; with saved credentials they show "Connecting to Wi-Fi" until connected or the same deadline, then the appropriate page address or access-point instructions. Recovery with no saved network exposes its access point immediately. Older main images without the hint use this recovery path.

The one-time migration requires USB and stable power because the partition table and bootloader change. All data partition addresses and sizes are retained. Use the migration manifest (no whole-flash erase or apps image); normal `flash` includes the preinstalled applications and replaces their partition. `app-flash` writes main at its explicit address and clears OTA metadata, leaving recovery and user data intact; start main with BACK. A normal first-install manifest carries both images and selects main on probation. Keep data still starts recovery; press BACK to try main. Recovery fixes require a deliberate USB maintenance operation: `recovery-flash` writes only factory and preserves main, OTA metadata and user data. The web flasher's Keep data mode can update both main and recovery on the existing layout as well as migrate the old one. Keep its protocol, layout descriptor and network keys compatible with future main releases.


### Catalogs
Applications are installed the way a Debian system installs packages: the device knows a few **sources**, each the address of a folder of static files, with an index in it; the index lists available packages, and the browser reads it. The device downloads prebuilt packages over HTTPS; it does not run Git or build applications. A source that is not `https://` is refused. Developers can use `tools/perinkpheral publish <folder> --repo owner/repository` to build and publish `catalog/` to their own public GitHub repository. The command uses Git and an authenticated GitHub CLI on the computer, preserves files outside `catalog/`, and prints the repository URL to add under Catalog > Sources. `catalog <folder> --out <dir>` remains available for other HTTPS hosting.
- `tools/perinkpheral catalog <folder> --out <catalog>` builds every application of a folder and writes `catalog.json` beside them: for each its name, title, version, `abi`, computed `firmware` minimum, and its files with their sizes and SHA-256.
- The official catalog is https://github.com/Perinkpheral/perinkpheral-apps: seventeen applications - `air`, `calendar`, `clock`, `donut`, `ha`, `iss`, `kit`, `life`, `metals`, `pomodoro`, `rates`, `status`, `stocks`, `stopwatch`, `sun`, `timer`, `weather`. Its `catalog/` is the fixed first source. The SDK's sample `hello` is in no catalog and no firmware image; `tools/perinkpheral run sdk/apps/hello` puts it on a development build.
- **Preinstalled** (the owner, 2026-11-21): a device flashed from scratch has `weather`, `clock`, `iss`, `calendar`, `timer`, `stopwatch`, `stocks` and `air` installed - ordinary catalog applications, removed and updated like any other. `firmware/preinstalled.properties` is the one place they are named: the catalog repository, the commit of it the packages are taken from, the applications. The firmware build (`tools/perinkpheral preinstalled build`, both flavours) takes each from that commit's committed `catalog/`, from a checkout that has the commit (`PERINKPHERAL_APPS`) or over HTTPS from raw.githubusercontent.com, keeps them under the build folder by the commit, checks every file against `catalog.json`'s size and SHA-256 as the device's installer does, refuses an unknown application, another ABI or a minimum firmware above the version being built, and an image the device's limits would not hold (24 applications, the code partition and aggregate filesystem capacity, including remaining writer reservations and the spare of `app_room.h`; it does not enforce the installer's per-application writer quota), and lays each out as an installation does: `<name>/<file>`, no commit mark. Standard `idf.py flash` writes `apps.bin` and replaces the apps partition on every use. OTA, `app-flash`, `recovery-flash` and the migration manifest preserve that partition. On the device they are installed applications from the first start: told `app_on_installed()` once, their module moved into the code partition. `tools/perinkpheral preinstalled bump` moves the pin to the catalog's main and says which versions change; the change is reviewed as an edit of that file.
- **As many as fit.** A device holds up to 24 applications, as much as their room allows (see Perinkpheral OS API); a catalog index may be at most 512 KB. The page installs and removes in a click, and **an application that is removed keeps what it stored** - its settings among it - for when it comes back (`&forget=1` on the removal erases that too), until the stores' partition is full: then what removed applications left is the first to go.
- The page passes the index on from the source as it comes (`GET /api/catalog?source=<n>`): the device streams it without parsing it for browser-driven browsing. Automatic updates parse catalog indexes in firmware with `catalog_stream`. Installing (`POST /api/apps/install`) downloads the files the index lists, takes each only if its size and SHA-256 are what the index says, reads the manifest with the parser that runs applications - one made for another `abi` is refused with those words. `app_store_commit_all` writes a commit marker before replacing files and removes it after the last replacement. A marked package stays unavailable until recovery finishes. Recovery and scene reload run together in the main event loop, so an incomplete package cannot run with mismatched files. Nothing restarts: Perinkpheral OS reads the list of applications anew (`host_reload_apps` - the scenes are made again, the poller's schedule too, and an application that was on the screen and is gone gives it to the menu). `GET` / `POST /api/sources` are the list. Install requests use `POST /api/apps/install?source=<index>&app=<name>` with `{"files":[{"name":"app.wasm","size":<bytes>,"sha256":"<hex>"},...],"version":"<expected version>","approved_authorities":<count>}`. The files list contains 2-8 unique files, with `app.wasm` first and `manifest.json` last. `version` is optional; when supplied, it must match the downloaded manifest. `approved_authorities` defaults to 0 and must match the manifest's certificate-authority count. A package requesting system access also requires confirmation on the device.
- There are no signatures: what vouches for an application is HTTPS to the source the user chose. The application is in the sandbox all the same.

### Power and profiles
The battery is connected. There is no detector of the power source in version 1, so the profile is a Perinkpheral OS setting, `power_saving`: 0 never (`plugged`, the default), 1 always (`battery`), 2 auto. It is in Settings on the device (General, Power saving: Disabled, Always, Auto) and on the page. **Auto** saves whenever no computer is on the USB cable, which is the one thing the board can tell (`usb_serial_jtag_is_connected`: USB host's packets, looked for every 5 s): plugged into a computer the device is as when plugged, otherwise as on its battery - and a charger looks like the battery. If a computer is connected while the device is asleep, press a device button so USB can enumerate and Auto can detect the connection.
- **plugged** - Wi-Fi always on, the web UI available, any `every`, polls on schedule.
- **battery** - **light sleep** between polls: memory, application state and the framebuffer are kept; wake-up by timer and by any of the four buttons (`gpio_wakeup_enable`). Wi-Fi comes up for the poll and goes down; the two-minute user-access window starts at power-up, is renewed by a button event, and is renewed when the effective power-saving state changes. The minimum `every` is 300 s, anything smaller is rounded up. Current and battery life have not been measured; battery life is not specified in version 1.
  - How it is built (`firmware/main/power.c`): the chip sleeps by itself whenever no task runs (ESP-IDF power management with tickless idle; `light_sleep_enable` follows the setting at run time). The radio is counted: the poller holds it while something waits for the network and gives it back after, a press holds it for two minutes, and with nobody holding it `wifi_set_radio(false)` stops Wi-Fi without the plan taking that for a lost network. A network that does not answer in 20 s is given up until the next poll's least distance. The buttons task waits for a level instead of sampling every 5 ms, or the chip would never sleep. The header's icon says how the last attempt went.
  - With a computer on the other end of the USB cable the chip does not sleep (`CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION`), so the console and flashing work on the bench - and so sleep itself has only been seen to be allowed, not seen: the radio's schedule was watched from the network, the current was not measured.
- **Deep sleep is deferred to version 2** (the owner, 2026-11-12). A cold start on every wake and no wake from button 4 require a separate design. Version 1 uses light sleep.

### TRMNL compatibility - as an application, not as a platform
The owner chose TRMNL compatibility as an application, with no changes to Perinkpheral OS. No `trmnl` application is implemented.

## Implemented architecture decisions

The owner's architecture decisions of 2026-11-12. The mechanisms below are implemented.

**Who may change what.**
- the main event loop owns Perinkpheral OS's state: the settings, the list of installed applications, the scenes. Every other task - the web server, the poller, Wi-Fi - reads a **published snapshot** of the settings and of the list, and changes nothing of them.
- A snapshot carries a version: a reader notes it, copies, and copies again if it changed meanwhile, with a compiler fence on each side of the copy; no lock on reading them. A reader may see what was true a moment ago.
- What a service keeps of its own is its own, under its own mutex: Wi-Fi's state, the status, the power profile, the display service, the poller's schedule and queue, the deadlines. the main event loop asks them like anybody else. The owner retained this division on 2026-11-15: the main event loop owns screens and applications; services own their state.
- A change is a **command through the event queue**: the handler posts it and waits for the main event loop's answer, as the development tools do. A page waits up to the length of a refresh; that is fine.
- Posting into the queue may be refused when it is full, and says so: the caller decides (a command answers "Device busy.", a deadline stays due, a press is lost).
- **Perinkpheral OS's settings are a store by key, and Settings is only one of its writers** (the owner, 2026-11-17: "settings must not know their consumers; another settings application must give the same behaviour"). Every setting is a line of one table (`appconf_fields()` in `firmware/components/appconf`, pure): its key - the one name it goes by on the page and in the system API, NVS keeping it under a short name of its own - its type, its range, whether it is a secret, whether it is taken at start, whether it is set its own way (the network, asked about on the device). `settings.c` is the store and nothing else: it reads and writes NVS by the table, checks a change whole, publishes the snapshot and tells whoever follows it (`settings_watch`), knowing none of them. Whoever puts a setting into effect follows the store itself: the clock and the panel (wired in `main.c`, for components that know no settings), the look - the typeface, the language, the greys - in the main event loop, the application runtime, power, the poller, the header. The page (`/api/settings`) and an application with system access (`sys_setting_*`) use the same validation rules; the application API exposes only its explicit allowlist of page-visible keys, never an internal setting such as `refresh_min_button_ms`; Settings is such an application and could be replaced by another.
- Package downloads are staged by the web waiting-handler task or the automatic-update task. The main event loop commits the package and reloads the application list.

**How an application is addressed.**
- Inside Perinkpheral OS an application is its **id: 31 bits of the SHA-256 of its module and manifest, never 0**. A new version is another application to everything that was waiting for the old one; the same package installed again is the same, regardless of version-string ordering. System applications are known by their names. The name stays for people and for the disk: the folder, the catalog, the page, the store, the application to return to after a restart.
- The schedule of polls, the requests and the alarms are kept **by id**. Removing an application removes its own; nothing else touches them.
- Several alarms per application: `alarm_set(id, seconds)`, `alarm_set_at(id, unix_time)`, `app_on_alarm(id)`.
- **Intents by subscription**: an application names in its manifest (`"intents"`) the kinds of news it wants, and gets them through `app_on_intent(type)`, loaded for it if it is not. Three kinds: the time changed (`time_changed`), the network is there again (`network_up`), and the device was powered up or restarted (`started`). **`started` is how an application runs without being opened**: a restart forgets alarms and requests under way (a poll's own pace is kept), and an application that asked is loaded off the screen after it and sets them going again from its store - a calendar puts its alarm back, a messenger makes its first request. Polls need none of this: they come from the manifest.  A kind Perinkpheral OS does not know fails the build (`tools/perinkpheral build`).
- `app_on_terminate()` is called before an instance is unloaded, whatever the reason - it left the screen, a delivery in the background is done, the device restarts, the application is removed - unless a fault stopped it, which ends it at once; light sleep keeps it loaded. `app_on_blur()` keeps its narrow meaning and comes first. State is saved in `app_on_terminate`.

**Time.** `firmware/components/deadlines` owns Perinkpheral OS deadlines. OTA probation, button debounce and network request timeouts keep their own timing.
- **One module owns the shared deadlines** of Perinkpheral OS and does nothing else: the polls, the alarms, the timers of the application on the screen, the panel's daily refresh, the while after a press, Wi-Fi's retries. Set a deadline, take it back, ask for the nearest; one that has come is an event in the queue.
- **The scale is absolute time.** The RTC always has one - the user's, the network's or 1970 - and runs through sleep. Behind the API everything is a moment: "in 20 minutes" is turned into one when it is set.
- When the clock is changed - by the network or by hand - deadlines that were set as "in so long" move with it, and those set as "at such a time" stay.

**Stopping.**
- A restart and a factory reset are one sequence in the main event loop: `app_on_terminate` for the loaded application, the panel's refresh to its end, the poller held, and only then the restart. Light sleep is no stop: ESP-IDF's power management, with everything loaded as it was. No waiting on the off chance: every step is known to be done.

**Memory.**
- `firmware/components/wasm3/m3_area.c` takes a 112 KB application area at start, reset whole on unload, as one heap for the module's memory and the interpreter's allocations. It was 128 KB (a 64 KB page and 64 KB for the interpreter, 2026-11-13) and 144 KB (80 KB for the interpreter, 2026-11-24), which left too little heap for Perinkpheral OS and TLS; since 2026-11-27 a module's memory is what it needs and the area is 112 KB. Reservation returns its actual availability to the caller; failure is logged, exposed by the additive `app_area_available` status field, and distinguished from transient memory pressure when an application cannot start. Applications use `-Oz` and link-time optimization; the interpreter uses 512-byte code pages. The build reports an estimate of interpreter use and warns if it exceeds the area. Exercise application paths on the device to check actual headroom.
- `firmware/main/app_code.c` maps the 320 KB code partition read-only. Modules occupy contiguous whole sectors after a 32-byte record. The size, name and check are written first, then the module, and only the four-byte magic is written last to commit it. If free sectors are fragmented, compaction first saves each moved module to its application folder; a restart imports that file again. The main event loop imports staged modules with no application loaded. Manifests, package files and stores stay in their own storage.
- An image carries the layout id made from `partitions.csv` (`image_layout.c`). OTA refuses an absent or different layout id before writing. A partition-table change requires a USB flash.
- TLS admission checks both total free heap and the largest contiguous block.

**The contract.**
- `http_send(tag, ...)`: the application chooses the tag, a number it has a name for, and the answer comes with it. Tags are an application's own; two applications with the same one never meet.
- An application asks for data; "there is no network" is one of the answers, and a request that failed says why: no network, no answer, a host the manifest does not allow.
- The header's icon says whether Wi-Fi has an address; with the radio asleep it keeps the latest connection attempt's outcome. A server, HTTP or TLS failure does not change it while Wi-Fi remains connected.
- The system API gives applications by id, not by their place in a list.
- `"system": true` stays one consent for all of it.
- `firmware/main/poller.c` connects four parts: which polls are wanted and at what pace (`poll_schedule.c`, pure - when each is due is a deadline, the alarms are deadlines outright), the one that talks to the network (`poller_net.c`), the requests applications make, waiting their turn (`firmware/components/appstore/request_queue.c`, pure), and what ties them to Perinkpheral OS (`poller.c`: the task, the radio). The task sleeps until it is woken and has no clock of its own. Calling the main event loop and waiting for it is `events_call_patiently()`.

Application memory is fixed rather than declared in each manifest. Perinkpheral OS keeps one instance and resets its arena on unload; moving allocations and compacting a runtime heap are outside this design.

The user manual is separate: `docs/manual/source/manual.html` and `manual.ru.txt`, built with `tools/perinkpheral manual [--language ru]`. The application guide and user manual are each built in English and Russian in CI and attached to releases. The English source governs. An API addition is documented in the application guide; a changed signature or meaning needs a new ABI.

### XML document queries (ABI 3, firmware 0.1.100)

Applications can query a complete application-owned document with `xml_child` and `xml_attr`, or project several attributes of one node with `xml_attrs`. Each call validates the current bytes. Results use preorder ordinals, valid for the same document. The strict attribute-only subset, input limits and status values are specified in `sdk/host/xml.h`. The implementation retains no application data between calls.

## Continuous integration
**CI runs on the organization's own runners** (the owner, 2026-11-20, after GitHub's hosted runners kept losing the package mirror): three of them, `perink-1` to `perink-3`, on one machine, labelled `perinkpheral`. A workflow asks for `[self-hosted, perinkpheral]`. The machine carries what the hosted image carried and a job used: a C compiler, Node.js, GitHub's CLI, Docker, Chromium's libraries, poppler-utils, the guide's fallback fonts, ffmpeg and webp; a job installs nothing with `sudo`. wasi-sdk and the Gradle home are kept in the runner's tool cache between runs. A whole run of this repository took 8.5 minutes on them against about 8 on GitHub's. Pull requests from forks wait for approval.

The owner's rule (2026-11-17): every push of every repository is built and tested; a push to `main` is also a release, with the version raised by itself; a push to another branch builds the same and releases nothing. The version of a release is the greater of the one the repository writes down (`VERSION`, `pluginVersion`, the integration's manifest; none for the catalog and the portal) and the highest matching version tag with its patch incremented. Non-main firmware, CLion plugin and Home Assistant integration artifacts use `<version>-<commit>`. Catalog packages retain their application versions; portal builds have no equivalent version stamp. Later runs may cancel earlier non-main runs. Runs of `main` go one at a time, so each takes the version the one before released. The notes of a release are the commits since the one before - for the firmware, the version's section of `CHANGES.md` when there is one.
- **This repository** (`.github/workflows/ci.yml`): the host tests with layer, language and city checks; `tools/core check`, including update-client, builder, publishing, author, preinstalled-package, capability, simulator, runtime, network-recovery, endurance and documentation regressions; CLI `pageTest`; and the firmware-update, application-request and application-settings browser tests; the applications of `firmware/test/sim` in the simulator, each frame held against a PNG that was looked at and kept (`tools/perinkpheral sim-test`; a frame that differs is the run's artifact, `--update` writes the pictures anew; the scenarios run several at a time, one a processor or `--jobs N`, and are told in their own order - each has a simulator, a port the system picked and a state folder of its own, its `wait` is real time, and one marked `"serial": true` runs while no other does); the firmware built twice in ESP-IDF's container - for release, and with the development tools for debugging (`<version>-debug`) - each with its separate recovery image and the files of a first flash, both with the same preinstalled applications, taken from a checkout of the catalog repository at the commit `firmware/preinstalled.properties` pins, which the job reads from there (`preinstalled pin`); the size of the image and of the RAM against the last build of `main`, in the run's summary and on a pull request. The printable-enclosure job checks the STEP source, 3MF geometry and archive with Python 3.12 and the CAD dependencies in `tools/case/requirements.txt`. A release carries both firmware builds and enclosure print files; then `flasher.yml` puts every release's firmware files on this repository's Pages for the flasher.
- **Generated files and guides** runs on a runner labelled `[self-hosted, perinkpheral]`, using Java 21, a C compiler, Chrome, poppler-utils and fallback fonts. The workflow does not pin the runner's operating-system version. Chrome prints the English and Russian editions of the application guide and user manual; poppler-utils extracts their text; fonts-dejavu-core, fonts-liberation and fonts-noto-core supply fallbacks, with Departure Mono in `assets/fonts`. CI requires complete Russian translations and matching guide limits, compares committed generated fonts, icons, marks and guide screen pixels, and checks the OpenAPI paths and methods against the firmware route tables. All four PDFs and glyph packs are release assets; glyph sheets are run artifacts.

## Conventions
- Everything is written strictly in English, with a plain hyphen `-`, never an en or em dash.
- **Interface text is short and standard**: on the panel, on the web page, in the answers of the API. The words every interface uses - Save, Update, Remove, Install, Factory reset, "Invalid value.", "Storage error." - and not a sentence of our own making ("Read them again", "refreshes nobody asked for"). No paragraphs of help under a field: a label that needs explaining is the wrong label. Simple, exact, competent.
- Nothing in the repository depends on one developer's machine: no home-directory paths, no fixed serial port names, no OS-specific steps in code, tools or documentation.
- **Single-source definitions checked by the build** (2026-11-14): a call's signature - in `sdk/host_api.h`, and Perinkpheral OS's table of imports is made from it (`tools/perinkpheral imports`, by the core's one reader of the contract); a task's priority and stack - in `firmware/components/board/include/priorities.h`; what is checked before a web handler runs - the request's origin, the memory - in the table of routes (`web_route_t`), and no handler repeats it; what is promised of the flash - the largest module, an install in hand beside the file system's spare, every store full - against `partitions.csv` in `firmware/main/flash_budget.c`, which does not compile when a number on either side breaks a promise; the guide's table of limits - against the headers, by `tools/perinkpheral check-limits` on every build of the guide. **The layers** (2026-11-17) - by `tools/perinkpheral check-layers` with the host tests: which component may know which, that none knows Perinkpheral OS's own code, that the pure modules know nothing of ESP-IDF, that the views and the scenes know no service, that the settings' store knows none of the settings' consumers, that the services know no screen, and that what the web server's handlers change of the main event loop's state they change through the main event loop. A new component, a new pure module or a new service is given its place in its tables when it is written. Time constants stay beside the code that uses them: most are a module's own pauses.
- JSON documents - manifests, the page's requests and answers - are read and written by `firmware/components/appstore/json_tree.c`, the project's own: a tree storing signed 64-bit integers without floating-point arithmetic. The parser accepts decimal fractions, retains their integer part and records whether the value was whole; exponent notation is rejected. Fields requiring integers must check `is_whole`. Answers that arrive in pieces are `sdk/lib/json_pick.c`.
- SPDX header in every source file, C11. Logic that does not need hardware is pure and host-tested; main's `settings.c` owns Perinkpheral OS's settings; recovery's `settings.c` only reads them through a read-only partition descriptor.
- When debugging hardware: the vendor's reference code and the datasheet first, hypotheses after. Do not suggest "check the wires".

## Branding
- **The logo is the word `perINKpheraL` set in the device's square font: lower case `per` and `phera`, capital `INK` and a capital `L` at the end, all of one height in the same squares, with no plate, frames or dots.** The capitalization is part of the wordmark. On the panel - black on white, scale 5 (27 px squares), 357 px.
- **The mark is two corners that frame an empty square**: the top right one and the bottom left one, a stroke each, set apart on the diagonal - the frame of a screen with nothing asking for attention in it. The owner found it on 2026-11-13 in Perinkpheral OS's own `update` icon (`gfx_icons.c`, eleven cells: each corner six cells across and six down, the two three cells apart; drawn six by six on 2026-11-17, at the owner's word) and named it the icon and the logo of the whole project. The word `perINKpheraL` stays the wordmark; the mark is what stands where a word does not fit - a favicon, an avatar, an icon of an application. It is made in `assets/mark` (SVG and PNG, bare and on paper) from the icon's own cells by `tools/perinkpheral mark`, which also gives the cells for the copies that stand in code (the portal's `Brand.tsx`, the device page's markup), and stands as the icon of the device's page in a browser, in the repository READMEs and as the icon of the Home Assistant integration. **It stays the `update` icon too** (the owner: "a superb decision that the icon is right there"): the question about a new firmware is asked under the project's own mark. **UPDATE retains this drawing at every display size.**
- The square font: every glyph is a square on a grid of 3 strokes × 2 gaps (5+6+5+6+5 = 27 px), no ascenders or descenders, diagonals allowed. Implementation: `firmware/components/gfx/font_square.c`.
- The splash at power-up is the About application's first page: the square-font wordmark, the build version below it, a QR code of the project address, and `(c) 2026 Max Grakov` and `MIT License` in the small font. When the application cannot be shown there is no splash: the device goes straight to where the splash would have led.
- **The square font is for the word `perINKpheraL` only.** All other device text uses the selected font family: Departure Mono by default, or Jersey. **Departure Mono** (SIL OFL 1.1, https://github.com/rektdeckard/departure-mono) is a monospaced pixel font. It is rasterized by `tools/perinkpheral font` once, at 11 px, where it lands on its own pixel grid; every size on the device is that bitmap with each dot drawn 1, 2, 3, 4, 6 or 10 pixels large, so a new size costs no flash. It was chosen on the panel against Jersey 20, Jersey 25 and Terminus. **Jersey** (SIL OFL 1.1, https://github.com/scfried/soft-type-jersey; heavier, proportional) is the second family the user can pick. The number in a Jersey face's name is the height of its capitals in pixels on its own grid, so Jersey 25 is the medium size and Jersey 15 the size of Perinkpheral OS's text; the files are `assets/fonts/Jersey{10,15,20,25}-Regular.ttf` with `OFL-Jersey.txt`. The file is `assets/fonts/DepartureMono-Regular.otf` with `OFL-DepartureMono.txt`. Departure Mono and Jersey are the approved device font families. Outline fonts rasterized to 1 bit (Tektur was the first try) come out thin and ragged at this pixel density - use fonts drawn for the pixel grid. Fonts are OFL/CC0 only.
- Palette: black #141413 and paper #E9E7E1 (on the device - the panel's native grey-white). Every Perinkpheral OS screen is black on white. Perinkpheral OS UI uses no halftones, dithering or gradients; applications may use dithered greys through `gfx_set_color`.
- Do not propose: a plate or frame around `INK`, dithered letters, white on black, decorations on the splash, other typefaces. Replacing Jersey was studied and closed (`docs/testing/jersey.md`): Tiny5 was tried in real screens on 2026-11-21 and rejected by the owner for its digits and its largest sizes.

## Do not
- Do not pull in Arduino, ESPHome, LVGL, GxEPD2, Home Assistant.
- Do not give applications sockets: the network is only `polls` - to the addresses the manifest writes - and `http_send` in Perinkpheral OS's queue, by the `hosts` list.
- Do not build a declarative JSON layout into the core (it can be one of the applications).
- Do not keep more than one wasm instance in memory or more than one TLS connection.
- Do not use pointer callbacks in the ABI - named exports only.
- Do not change an existing ABI 3 signature, meaning, privilege, layout or constant without a new `abi`, except for `HOST_ICON_COUNT` growth with contiguous appended icon IDs and the explicitly authorized pre-release exception described above. Additions require a recorded snapshot and applicable `HOST_SINCE_<name>` stamps.
- Do not design for PSRAM: there is none.
- Do not measure battery voltage or detect USB supply voltage - no dividers or ADC, decided. The existing USB-host connection check for Auto is not a measurement of the power source.
- Do not "optimize" the panel driver past Waveshare's own: its commands, its waveforms and its waits as they are, CS per byte, bounded BUSY waits. No waveforms of our own (`0x32`).
