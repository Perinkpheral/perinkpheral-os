# Stress run, 2026-11-27

The aim was to find a load that makes the device fail and record the limits.
Each axis ramps one kind of load and stops at the first unrequested restart, panic,
watchdog reset or allocation failure. Unlike the [load plan](load.md), nothing runs
for hours.

## Setup

- Device: the owner's unit, on USB power, Wi-Fi to the home access point (channel 11, -67 dBm).
- Images: release 0.1.101 (`65b0bccd…`) for axis A. The 0.1.101 development build for
  axes C-E. Local development builds of `fix/stop-unwanted-stream` for the checks of the
  fix and for axes B, F and G. Release 0.1.101 was written back at the end.
- Installed: the 13 catalog applications plus bench applications. `stress` (22 KB
  memory), `stressfat` (62 KB memory, area 81 of 112 KB) and `stressdoc` (documents
  only) polled a hostile HTTP server on the bench computer every 10 s.
- Observation: `/api/status` before and after every step, and the USB console read
  without resetting the chip.
- A full flash copy was taken before the run.

## Results

| Axis | Load at its highest | Outcome |
|---|---|---|
| A. Web server | 64 parallel GETs; 24 clients sending one byte every 0.5 s; 32 idle sockets; headers and URIs over the limit; 200 KB bodies and bodies declared at 1 GB to every POST route | No failure. Answers 408/414/431/400; sockets beyond the limit are refused at accept and freed by the 10 s receive timeout |
| B. Host memory | 8 catalog reads, 8 reinstalls and 8 Latin pack uploads at once, 16 page loops, while applications poll over TLS | No restart. Refusals (503 busy/memory) as designed. Lowest free heap 12.8 KB. At 20 heavy clients, one allocation failed: 1679 bytes, internal DMA memory, a Wi-Fi transmit buffer (one packet dropped). `httpd` starves the idle task (task watchdog message, no reset) and the page stops answering while the load lasts |
| C. Hostile answers | 50 cases on pick, document, XML and raw polls: 255/300 KB, nesting to 50 000, 20 000 keys, invalid UTF-8, lone surrogates, lying/negative/huge Content-Length, 200 headers of 900 bytes, endless and trickling streams, stalls, resets, redirect loops, XML entities, 65 attributes, 20 000-byte names | No failure. One defect: an endless answer to a document poll held the device's only connection for 300 s (fixed, below) |
| D. Misbehaving application | 16 queued requests refilled on completion; requests to a stalled server; files and store to their limits; 1 ms timers; redraw every 1 ms; recursion 100 000 deep; out-of-bounds read; endless loop in handlers; 62 KB memory | No failure. A handler is stopped after 3 s. Handlers called back to back (settings, then focus) hold the host loop over 5 s: task watchdog message, no reset |
| E. Navigation | 1911 UP/DOWN presses with no pause; 338 BACK-held switches; 59 application opens back to back; mixed | No failure. An open takes 1.2-3 s and paces itself |

No load produced a panic, a watchdog reset or an unrequested restart.

## Found and fixed

On branch `fix/stop-unwanted-stream`:

- **A streamed answer that nobody takes is no longer read to its end.** Before, the
  poller read up to 4 MB or for 300 s even when the instance that took the first
  piece was gone. That happens when the user leaves the application, when it has
  stopped, or when it reads only a document that has already failed or been refused.
  All polls of all applications, catalog reads and installations waited behind it.
  - Measured with an endless answer: the connection was held 307 s before the fix,
    1.7 s after it on a document poll, and 3.5 s after one long BACK.
- **The failed-allocation hook keeps the size, caps and heap function** of the last
  failure, and the short-of-memory warning names them. Before, a failure could only
  be counted.

## Limits

- One connection: a raw stream that its application keeps reading may hold it for
  300 s, as the contract allows.
- An application looping in `app_on_data` in the background costs 3 s of the host
  loop per delivery. With 10 s polls, opening an application took up to 4.3 s
  instead of 1.6 s. The application is stopped each time and loaded again for the
  next answer.
- A flood of 20 or more heavy clients from the home network makes the page
  unavailable for its duration. The device recovers when it stops. SECURITY.md
  promises no defence against the home network.
