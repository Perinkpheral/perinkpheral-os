# 0011: Application page 64 to 32 KiB; dynamic linear memory deferred

Date: 2026-11-26

Status: accepted (page); deferred (dynamic linear memory)

## Context

The application area is one block reserved from the heap at start: one page
for the module's linear memory plus 80 KiB of interpreter working space
([0001](0001-interpreter-arena.md)). With the 64 KiB page the block was
144 KiB, and the device ran under its admission gate: TLS requests were
refused with "Device busy". [0007](0007-ram-savings.md) kept the 144 KiB
area and found no savings elsewhere worth taking. The question here was the
page itself: how much of it applications actually use.

## Decision

The page goes to 32 KiB, so the area is 112 KiB. Modules declare the smaller
memory with the custom one-byte wasm page (`wasm-ld --page-size=1`; the
linker accepts only 1 or 65536, and the resulting memory section is
flags=9, initial=32768, max=32768, log_page=0, which wasm3 reads natively).
The builder checks the module's memory in bytes, and the host refuses a
module whose memory is not the area's page exactly, so a module linked for
another page size cannot take the interpreter's working space.

The owner allowed the ABI 3 memory break before the first public release:
every published module must be rebuilt.

Dynamic linear memory — `initial` at the linker's static size with
`max` 32 KiB and `memory.grow` gated inside the area — was proposed in the
same discussion and **deferred** by the owner on 2026-11-26: there is no
pressure that pays for it now. See below.

## Evidence

Measured on the device (ESP32-C6, firmware from `feature/page-32k`,
version string `0.1.100-296557b`, ESP-IDF 5.5.5, wasi-sdk 34), 2026-11-26:

| | 64 KiB page (main) | 32 KiB page |
| --- | --- | --- |
| area block | 147,456 bytes | 114,688 bytes |
| least free heap during use | about 17.4 KiB | 33,388–34,100 bytes |
| memory refusals | 50 | 0 |
| largest free block | — | 51,200–71,680 bytes |

"Device busy" did not reappear in use. Weather, ha, stocks, space-launch
and earthquakes ran their real data paths on the device with the 32 KiB
page; screenshots and logs are in the working record.

The interpreter estimate is the builder's advisory figure, not a measured
peak. The page does not relieve it: the scarce resource for large
applications remains the interpreter's 80 KiB.

Two findings shaped the decision:

- No catalog application calls `app_alloc` (grep over the catalog).
  Linear use is static data plus stack, fixed at link time; there is no
  runtime peak to measure, and the 64 KiB page was mostly idle reservation.
- calendar did not fit as it was: 45,200 bytes of static data in 200
  fixed-size event slots, each with a 127-byte title. A first cut of the
  title to 63 bytes fitted but showed on the event screen (31 Cyrillic
  characters of a four-line title) and was not taken. Calendar 0.6.0 keeps
  127-byte titles: kept events are 32 bytes with titles packed per source.

earthquakes showing "no answer" was checked and is data, not memory: the
USGS feed within 1000 km of the configured place returned zero features
at the time, and the same application failed the same scenarios in the
64 KiB simulator baseline.

## Consequences

- The area is 112 KiB; admission reserves the worst case once at start, so
  a loaded application can never run out of linear memory.
- ABI 3 modules built for the 64 KiB page are refused at load. The catalog,
  the preinstalled partition and the simulators bundled with the IDE plugin
  must be rebuilt and republished; until then an old module on a device
  fails to open, which is the intended refusal.
- Four applications have under 8 KiB of page headroom (table above).

## "Device busy" on the device page

The measurements above were taken before this was separated, and the page
alone did not remove it. A waiting web route that needs a session
(`/api/catalog`, `/api/apps/install`) was asked for 60 KiB of free heap on
arrival. Its download is the poller's and runs after the poll in progress,
so on arrival the question was answered by that poll's own TLS session: the
request was refused although it only had to wait its turn, and the page's
three retries could each land in the next poll of a round.

Decision: on arrival such a route is asked only for a page's worth (24 KiB
free, 8 KiB in one block), for what its handler allocates before the
download; the poller asks for the session's room when the download's turn
comes and waits up to six seconds, as it did. Its looks while waiting are
uncounted (`memory_peek`) and, when they see room, end the refused period
the ten-minute restart watches; a refusal is counted once.

Consequence: the request waits as long as the poll in front of it - up to
a minute for a picked answer, five for a streamed one - and holds the single
waiting slot, so another waiting route answers "Device busy." meanwhile.
Before, it was refused within the page's 14 s of retries.

Not taken: a first form that kept the question on arrival and waited for
room on the request's task for up to 20 s, with a flag holding the poller's
polls back. It was verified once on the device, but duplicated the ordering
the poller already gives and held the single waiting slot for the length of
the wait. The form taken has host tests (`test_web_memory.c`,
`test_poller.c`, `test_memory.c`), was reviewed blind, and has not yet been
run on the device.

## Deferred: dynamic linear memory

Proposal: link with `initial` at the linker's static size and `max` 32 KiB;
wasm3 supports `memory.grow` with the custom page size, and the area
already holds a private heap, so grow could be gated on the area's free
space without touching the main heap.

Expected saving: 7–22 KiB per load (one application occupies the area at a
time), against 33 KiB of measured least-free headroom. Costs: admission
could no longer promise linear memory for the life of a loaded application
(a grow could fail mid-request, which is where "Device busy" hurt most);
variable-size blocks in the main heap if the area block itself were sized
per load; builder and host changes plus their tests, immediately after the
system had stabilized.

The owner agreed there was no reason to take it now. The safe form if it
returns: `initial` at static size, `max` 32 KiB, area unchanged at 112 KiB,
grow bounded by the area — no new main-heap failure mode, and the host
check becomes `<= page` with grow gated on the area's free space.

## Reopen when

Heap pressure returns: least-free headroom under roughly 20 KiB in normal
use, or refusals reappear in the [endurance](../testing/stability.md) or
[load](../testing/load.md) tests. Then take the deferred form above rather
than growing the page back.
