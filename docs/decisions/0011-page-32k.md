# 0011: Application memory sized to need; area 144 to 112 KiB

Date: 2026-11-26, revised 2026-11-27

Status: accepted

## Context

The application area is one block reserved from the heap at start. It was
144 KiB: a 64 KiB page for the module's linear memory plus 80 KiB of
interpreter working space ([0001](0001-interpreter-arena.md)). The device
ran under its admission gate: TLS requests were refused with "Device busy".
[0007](0007-ram-savings.md) kept the 144 KiB area and found no savings
elsewhere worth taking. Perinkpheral OS needs more free heap, while large
applications need more than 80 KiB for the interpreter.

## Decision

A module's linear memory is what its stack and data take, to the byte, at
most one standard page of 64 KiB; the builder links it so that it cannot
grow. The area is 112 KiB.

The area is one heap (`m3_area.c`): the module's memory and every
interpreter allocation are taken from it. The split into "page" and
"interpreter" existed only as a check at load, so what a module does not
declare is the interpreter's without any further mechanism.

- Link: `wasm-ld --page-size=1 --no-growable-memory` (the linker accepts a
  page size of 1 or 65536; wasm3 reads the custom page size natively). The
  memory section declares initial = max = the size of the stack and data.
- Builder: refuses a memory that may grow or exceeds 64 KiB; reports the
  memory and the estimate of the running code together against 112 KiB.
- Perinkpheral OS: validates the memory declaration before interpreter allocation,
  including modules built outside the SDK. As in the builder, linear memory must
  have a maximum equal to its initial size and must not exceed 64 KiB; growable
  or oversized declarations return `APP_ERR_BAD_MODULE`. Fixed modules linked for
  one standard 64 KiB page remain accepted by the memory-size limit, including
  the frozen ABI 3 fixtures. Loading and execution still require linear memory,
  interpreter allocations and contract scratch memory to fit the shared 112 KiB area.
- `app_alloc()`: the arena is declared by the application,
  `APP_ALLOC_ARENA(bytes)`, and is static data. Before, it was whatever the
  fixed page had left. No catalog application allocates.

## Path

1. 2026-11-26: a fixed 32 KiB page (area 112 KiB), with Perinkpheral OS refusing
   any other size. It returned the heap to Perinkpheral OS, measured below, but
   gave applications nothing and made every published module unloadable.
   Calendar did not fit (45,200 bytes of static data).
2. 2026-11-27, the owner's hypothesis: allocate what is required, up to a
   limit. Verified on the device the same night and taken instead of 1.
   Growing at run time (`memory.grow` gated on the area) was considered and
   not taken: no application allocates at run time, and a grow that fails in
   the middle of a request is the failure admission exists to prevent.

## Evidence

Measured on the device (ESP32-C6, ESP-IDF 5.5.5, wasi-sdk 34).

Perinkpheral OS heap, 64 KiB page and 144 KiB area against a 112 KiB area, 2026-11-26:

| | 144 KiB area | 112 KiB area |
| --- | --- | --- |
| area block | 147,456 bytes | 114,688 bytes |
| least free heap during use | about 17.4 KiB | 32-38 KiB |
| memory refusals | 50 | 0 |

Peak of the area (`app_area_used`), the same firmware and the same
application linked with a 32 KiB page and with memory sized to need,
2026-11-27:

| Application | 32 KiB page | To need | Freed |
| --- | --- | --- | --- |
| weather | 66,668 | 43,820 | 22,848 |
| earthquakes | 92,932 | 81,824 | 11,108 |
| space-launch | 89,196 | 82,044 | 7,152 |

Perinkpheral OS's least free heap was the same in both (about 32 KiB), with no
refusals and no failed allocations. The earthquakes figures depend on the
data that arrived and are approximate.

The builder's report for the catalog, 2026-11-27, of the 112 KiB area:
memory, the advisory estimate of the running code, and their sum.

| Application | Memory, KiB | Code estimate, KiB | Sum, KiB |
| --- | --- | --- | --- |
| calendar | 37.3 | 70.9 | 108.1 |
| earthquakes | 18.4 | 83.8 | 102.2 |
| space-launch | 25.0 | 74.3 | 99.3 |
| keenetic | 16.0 | 73.5 | 89.4 |
| rates | 19.0 | 66.3 | 85.3 |
| the other 14 | 9.0-28.3 | 13.1-47.4 | under 60 |

The estimate assumes all of the code runs and is well above measured use:
keenetic's whole area peaked at 76,536 bytes over its four screens.

Calendar keeps 127-byte titles with kept events of 32 bytes and titles
packed per source. A first cut of titles to 63 bytes showed on the event
screen (31 Cyrillic characters of a four-line title) and was not taken.

## Consequences

- An application with little data has more room for code: weather has about
  102 KiB of the area left for the interpreter, where it had 80.
- A module still linked for a 64 KiB page has 48 KiB left for the interpreter,
  where it had 80. A large application built before 0.1.101 may fail to load
  or run; it is rebuilt with this SDK. There is no compatibility for modules
  built before the first release.
- The builder's sum is advisory, as the code estimate is. An application
  near 112 KiB is exercised on the device.

## "Device busy" on the device page

Catalog and installation routes (`/api/catalog`, `/api/apps/install`) previously
required session-level memory admission on arrival, allowing an active poll to
cause premature refusal. The page's three retries could each overlap a later
poll in the same round. The measurements above preceded this admission change.

Decision: these routes require page-level admission on arrival: 24 KiB free and
an 8 KiB contiguous block. After the preceding poll finishes, the poller applies
session admission and waits up to six seconds for memory. Observations during
that wait use `memory_peek` and do not count as refusals. An observation of
sufficient memory clears the refusal period used by the ten-minute restart
threshold; a final refusal is counted once.

Consequence: the request waits for the poll in front of it and holds the
single waiting slot, so another waiting route answers `503` "Device busy."
meanwhile. The poll's body deadline is 60 seconds for a picked answer and
300 seconds for a streamed one. Connection setup, headers and delivery add
to the elapsed wait; these deadlines do not bound the total wait. The
[stress run](../testing/stress-2026-11-27.md) measured 307 seconds for an
endless answer before unwanted streams were stopped early.
Before, it was refused within the page's 14 s of retries.

Not taken: a first form that kept the question on arrival and waited for
room on the request's task for up to 20 s, with a flag holding the poller's
polls back. It was verified once on the device, but duplicated the ordering
the poller already gives and held the single waiting slot for the length of
the wait. The form taken has host tests (`test_web_memory.c`,
`test_poller.c`, `test_memory.c`). Axis B of the
[stress run](../testing/stress-2026-11-27.md) exercised catalog reads and
installs during TLS polling on the device. It recorded expected busy and
memory refusals without a restart; at 20 heavy clients a Wi-Fi transmit
allocation failed and the page stopped answering for the duration of the
load. Sustained qualification under the [load plan](../testing/load.md),
including its TLS/queue scenario L7, remains unrun.

## Reopen when

Heap pressure returns: least-free headroom under roughly 20 KiB in normal
use, or refusals reappear in the [endurance](../testing/stability.md) or
[load](../testing/load.md) tests. The area's size is then the question; a
module's memory is already as small as it can be.
